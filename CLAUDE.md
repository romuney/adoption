# CLAUDE.md

Это рабочая папка BI-проекта «Proteus Adoption» — перестройка боевого дашборда
13896 внутри корпоративного BI **Proteus** (форк Superset: eCharts-виджеты с
кастомным JS, viz_type `react_sanbbox`). Это не приложение и до передачи не
было git-репозиторием: здесь живут макет, виджеты, генераторы SQL и стенды, а
боевая система правится владельцем руками в UI Proteus по инструкциям из папок
поставки.

Общий гайд по бордам Proteus — romuney/TeamPulse, ветка claude/proteus-playbook, папка proteus-playbook/: SKILL.md — вход.

**Начни с `CONTEXT.md`** — полный контекст проекта на 2026-09-22 (§0 — v7): живой статус,
архитектура, вердикты, грабли платформы и ClickHouse, правила владельца,
открытые хвосты. Здесь — только навигация и команды.

## Конвенции

- Правки боевого Proteus вносит владелец вручную: любая доставка — папка
  `Обновление <дата> (<версия>): <суть>` с `0. Инструкция.md` и нумерованными
  файлами; в инструкции — шаги с проверками и стоп-точками («красное →
  прислать текст ошибки целиком»).
- Именование: точка-префикс в корне = живой инструмент из белого списка;
  `_`-префикс = служебное; цифры «1. 2. 3.» = файлы поставки.
- **Скратч не копить**: дампы, пробы, тестовые проходы удаляются сразу по
  закрытии этапа; опыт фиксируется финальным правилом (в CLAUDE.md / память),
  не историей итераций.
- Типографика: **шрифт — только Arial** (на бою другого нет, владелец 2026-10-09): стек `Arial,Helvetica,sans-serif`,
  веса только 400 и 700; кегли — шкала DESIGN_SYSTEM §16.2 (с 09.10 на ступень мельче); минус типографский; разряды
  тонким пробелом. Стенд: Inter в контейнере установлен — без стека Arial скриншоты не совпадают с боем.
- `Виджеты/*.NOTES.md` — точка восстановления после обрыва сессии: прочитать
  целиком, найти первый пункт плана ≠ DONE и продолжать с него.
- SQL-шаблоны куба правятся ТОЛЬКО генераторами (`.gen_*.py`), не руками;
  после правки — прогон jinja-стенда, перед боем — прогон дефолт-рендера в
  SQL Lab владельцем (стенды не исполняют SQL, см. CONTEXT.md §9).
- Существенные факты фиксировать в долгой памяти, не только в чате.
- **SQL под лексер Proteus (09.10: Superset 2.1.0, sqlparse 0.4.3 + патч):** литерал `[…]` — только без «]» внутри
  (sqlparse читает `[` как имя до первой «]»: значение `a]b` давало Code 36). Макрос `qa` сам выбирает `array(…)`, если
  в значениях есть «]»; регулярки в коде — без классов `[…]` (`'^(?:\\s|\\p{P})*$'` в `ou`/`ous` и шапке). Проверка —
  kit `superset201.py --hostile` на файлах 3, 5, 7. Обёртка чарта — `GROUP BY` всех «Измерений» и `LIMIT 50000`: порядок
  строк не держится, строки собирать в `k` через `arraySort(groupArray(…))` (каталог pa_body_one, 09.10).
- **JS в папке единого листа — сжатая сборка** (09.10): код чарта едет в каждом `chart/data`; править `Виджеты/*.chart.js`,
  собирать `.stand/pack.py`.
- **ОБЯЗАТЕЛЬНО — «один запрос, два чарта»** (решение владельца 2026-09-30): числа, зависящие от собственного выбора
  чарта A (самовлияние выключено), считает датасет соседнего чарта B, который и так перезапрашивается на этот выбор
  (новая секция в его ответе), и шлёт A через PA-канал (postMessage, ключ из эха flt, ASK + переспрос, B отвечает
  всегда, в A — таймаут и пометка с причиной вместо пустоты). Не самовлияние, не новый запрос, не предрасчёт матриц
  в браузер. Эталон — секция `aa` pa_one → вкладка «Аудитория» каталога (PA_AUD), регресс check_one §10.
  Логику не дублировать: общие выражения — jinja-макросы, число и список — из одного набора, правила новой секции ==
  существующей (доказать регрессом). SQL и JS чарта поставляются парой; после вставки — Save и Cmd+Shift+R.
