Принцип раскладки: в ОДИН чарт — всё, что считается из одного ответа и
должно переключаться мгновенно (у панели: список, дерево, корзины, динамика,
когорты, KPI — одна область, одна гранулярность «люди»); отдельный датасет —
только там, где гранулярность другая и нужна серверная дедупликация
(каталог = строки отчётов под людским фильтром; панель = люди под фильтром
отчётов). Две шины крест-накрест, самовлияние у всех выключено.

**SQL v7** (правится напрямую в `Виджеты/*.data.sql`, генераторов в репо нет):
- Каталог читает **`prod_proteus.pa_pair`** — новый GP-предагрегат: строка
  на пару «отчёт × логин», у пары 64-битная маска активных бакетов
  (`msk_d/w/m/q`, bit k = активен в бакете возраста k < 2n), суммы окна,
  `v_life`, `dmax`, `own_flg`, `md`. Маски зависят только от даты свежести →
  считаются раз в сутки. Все счётчики периода = `bitCount` по OR масок, ни один
  GROUP BY не несёт бакет. Запасной вариант на дневном факте (файл 2b) даёт
  те же числа (приём масок без GP).
- `pa_people`: одно чтение дневного факта → одна строка на зрителя (маска,
  дни, sumMap просмотров по бакетам, месяцы активности) → роли строки
  (total/freq/ctx/list/ts/coh) одним `arrayJoin` → один GROUP BY → лимиты
  секций `row_number()`. UNION-плеч над общим CTE нет (у pa_who их было 10 →
  11 чтений факта, у pa_aud 7).
- Семантика выровнена: корзины частоты и «постоянные» = АКТИВНЫЕ ПЕРИОДЫ
  грануляции везде (каталог, панель, фильтр `freq_f`); «ушедшие» (`sleeping`)
  = были в прошлом периоде, в текущем нет; сравнение с прошлым периодом —
  только d/w (m/q не помещаются в 13 мес. истории).
- Массив для `has/hasAny` — макрос `qa()`: `where_in` даёт кортеж или скаляр,
  `hasAny(arr, ('a','b'))` падает (так падали фильтр AD-группы в v6 и выбор
  коллекции в pa_who).

## 4. Архитектура листа 2.5 (три шины кросс-фильтров)

Раскладка: полоска настроек сверху → тело слева (~30–40% ширины: каталог 3
разреза + KPI + чипы условий) → «Кто смотрит» ⇄ «Динамика» справа → когорты
полноширинно. v5-наследие: один ответ куба несёт ВСЕ разрезы, смена вкладки —
клиентская.

1. **Шина полоски** (`period_param`, `pub_f`/`act_f`/`exc_f`): полоска эмитит →
   тело, когорты, pa-who. Сама сидит на pa_dicts (лимит 1 строка).
2. **Отчётная шина каталога** (`mode_param` + `sel_f`): клики по строкам
   каталога тела → когорты, pa-who, панель Аудитории. Тело себя НЕ
   перечитывает (самовлияние выключено — решение владельца, см. §8).
3. **Людская шина** (`login_f`/`lvl3_f`/`lvl4_f`/`spec_f`/`stream_f`/`adg_f`/
   `heads_f`/`freq_f`): клики людей/групп/корзин в pa-who → ТОЛЬКО тело.
   pa-who себя не сужает (BI-паттерн: источник не фильтрует себя).

Ключевое следствие архитектуры: **два датасета = два ПАРАЛЛЕЛЬНЫХ запроса**,
пользователь ждёт max(куб; люди). Это доказано замером и закрыло вопрос
«одним датасетом» (§7).

Производные величины (доли, медианы когорт, MAU, freq-срез, дедуп
микс-выбора) считаются в JS (`buildModel`), SQL отдаёт сырые строки. Числа
между вкладками обязаны сходиться — источник один.

## 5. Куб v6: как устроен

`.gen_cube6.py` (генератор; шаблоны `.pa6_*.sql` правятся ТОЛЬКО им) →
`.pa6_body.sql` (джиня-шаблон тела) + `.pa6_coh.sql` (когорты) + дефолт-рендеры
`*_default.sql` (эталоны для SQL Lab и стендов). Джиня читает кросс-фильтры
через `filter_values(...)`: период, свитки полоски, людская шина (`ppla`
CTE — свой скан факта с теми же условиями вселенной), sel-маска области.
`state_j` — JSON активных условий у total-строки (37-я колонка), чипы в теле.

Цепочка (после ускорения 2026-09-22): `maxd → dash_ok → evd → b1 → pa → agg →
OUTER`. Приёмы: ключ строки размножается `arrayJoin` набора `(kd, k0)` —
0=total, 1=отчёт, 2=владелец, 3=коллекция (в v6 ов-разрезов lvl3/spec НЕТ —
людские разрезы живут в pa-who); динамика — 4×`sumMap` по одному массиву
`kvw`; «вернувшиеся» = `arrayCount(j -> j > k AND j <= k+gap, ks_all) = 0`;
первый визит `fd_k = max(kmax)`; частотные корзины `countIf(days_cur …)`.

Когорты (`.pa6_coh.sql`): глобальные 12×12 + rcoh/gcoh выбранной области,
людскую шину НЕ читают (архитектура 2.5), CUTS — прямые колонки attrs.
Когортам нужна ВСЯ история — свёртка хвоста к ним НЕ применяется.

## 6. Ускорение v6 от 2026-09-22 (перенесено в поставку)

Две правки цепочки, обе доказаны контрольными суммами (обе версии обёрнуты в
один SELECT по 17 величинам — строки, users/views/new/sleeping/regular, суммы
корзин, длины и суммы всех ts_*, границы last_view_days; все 17 совпали до
единицы, вкл. `max(last_view_days)=347` — самый чувствительный к потере
старых бакетов):

1. **`b0` слит в `evd`**: предагрегат уже дневной, при grain='d' отдельный
   проход «разложить по бакетам» отдавал ровно столько же строк, сколько
   принимал (6 868 576 → 6 868 576), +0,88 с впустую. Бакет считается сразу
   в первом GROUP BY по сырому факту.
2. **Хвост старше окна свёрнут в бакет `k = -1`**: `if(kexpr < n2, kexpr,
   -1)`, первый визит несётся отдельным `max(kexpr) AS kmax`. Год истории
   больше не проходит через размножение ключа ×4,6: b1 было 31,5 млн строк →
   8,8 млн; цепочка 11,39 → 3,21 с. **Во всех оконных условиях обязан порог
   `k >= 0`** — без него свёрнутый хвост утекает в текущий период и ТИХО
   портит цифры.

Грабли рядом: возраст бакета нельзя вынести алиасом (колонка вне GROUP BY —
CH отклоняет), выражение подставляется дважды. Замеры на цепочке: evd 1,16 /
+b1 2,09 / +pa 3,21 / +res 4,21 с; итог каталога ~5,7 с (объединённая форма
v7), боевой v6 до правок — 2,22 с на прогретых данных (16,42 с холодный
первый прогон). Замеры шли через SQL Lab владельца.

## 7. Вердикт «один датасет» (закрыт 2026-09-22)

Вопрос владельца: «вся верхняя история (куб+люди) одним датасетом/чартом?»
Прототип v7 (49 колонок = 37 куба + 12 людских, люди через размножение РОЛИ
строки `arrayJoin` + один GROUP BY, без UNION) собран, замерен, **отвергнут**:
полный ответ 8 с против ~2,2 с у нынешней схемы из двух датасетов. Причина
структурная: экран ждёт `max()` двух параллельных запросов, объединение платит
сумму работ, экономя только скан факта (1,2 из 5,7 с). Попутные находки
сохранены: людской агрегат уже лежит в `pa` при kd=0 (шина «итого»), пара
человек×отчёт — при kd=1; `days` = uniqExactIf по бакетам (не countIf — тот
считал ПАРЫ отчёт×день, грабля pa_who 22.09: «1614 дней» за 30-дневное окно
физически невозможно — сравнивать числа с физическими пределами).

## 8. Платформа Proteus: главные факты и грабли

Живой прецедент всей механики — борд 59922 (чарты 783469/783708, датасет
168383). Всё ниже проверено на нём или на нашем борде.

**Кросс-фильтры.** `applyCrossFilter([{column, operator:'IN', value:[…]}])`
из JS виджета доезжает до `filter_values('col')` в джине виртуального
датасета. Носитель-колонку НЕ выводят в SELECT — иначе Superset навесит
авто-IN на внешний запрос (для ARRAY-колонок CH это роняет запрос). Грабли
эмиттов: operator ОБЯЗАТЕЛЕН (без него 400 «Missing op» и валятся ВСЕ
получатели); пустой value=[] НЕ эмитить (роняет запрос чарта), но
`applyCrossFilter([])` как ПОЛНАЯ очистка — работает; возврат к дефолту —
кнопкой-пресетом в виджете.

**Скоупы решают всё** (`json_metadata → chart_configuration.<id>.
crossFilters.scope`): `{rootPath, excluded:[…], chartsInScope:[…]}`.
Самовлияние — НЕ дефолт платформы, а настройка: убрать себя из `excluded`
(на 59922 так и сделано; в v3 наши клики были серверными ~1,2 с). У нас
самовлияние тела ВЫКЛЮЧЕНО владельцем — требование, не баг. Настройка скоупа
— на весь чарт, разделить «клик без самовлияния / смена разреза с
самовлиянием» платформа не даёт. Инструмент MCP: `proteus_filters
action='set_cross'` (dashboard обязателен, source/target — ИМЕНА чартов);
проверять `action='list'`. **set_cross ПЕРСИСТЕНТЕН на драфте** —
экспериментальную маску обязательно снимать.

**DOM/рендер оверлея.** `overlay` — скролл-контейнер: любой
`overlay.innerHTML` сбрасывает scrollTop → сохранять/восстанавливать.
`viewBox + width:100%` масштабирует ШРИФТЫ (11px→20px) — мерить ширину после
монта (`clientWidth`) и пересобирать разметку с viewBox == clientWidth.
Аккордеон: раскрываемое тело — СЕСТРИНСКИЙ узел шапки (`act.parentNode`).
`render()` объявлена внутри `mount()` — наружу через `var rerender`.
Данные: глобальный массив `data` (все строки). Виджет живёт в iframe-sandbox:
попапы не выходят за границы без CSS-хака родителя.

**Встраивание/шов.** Цепочка:
`.dashboard-grid → … → .resizable-container → .dashboard-component-chart-holder
→ .chart-slice → .chart-container → .react_sanbbox → iframe`. Рабочая CSS-вставка
(раунды 11+12, подтверждена живым бордом, шов 16px): `.chart-slice
{display:flex;flex-direction:column}`, `iframe{display:block}`,
`.dashboard-component-chart-holder{padding:0!important}` (ГЛАВНЫЙ фикс —
emotion-паддинг 16px форка), `.chart-container{padding:0!important}`,
`.grid-content > :not(:last-child){margin-bottom:16px!important}`.

## 9. ClickHouse 24: пределы и приёмы

Полная версия — `memory/clickhouse24-proteus-limits.md`. Выжимка:

- **CTE инлайнится в каждую точку ссылки** (~×5,5 на 6 ссылок). `AS
  MATERIALIZED` и `SETTINGS` в теле датасета НЕДОСТУПНЫ (версия 24 + обёртка
  Proteus). ⇒ запрос = ЛИНЕЙНАЯ ЦЕПОЧКА, каждый CTE — одна ссылка; скалярный
  подзапрос считается однажды; ветвление — размножением КЛЮЧА (`arrayJoin`),
  не цепочки. Плечи UNION поверх общего CTE — ЗАПРЕЩЕНЫ (v7.0: 8 плеч по pb →
  факт сканировался 17 раз → тайм-аут).
- **Замер = ТОЛЬКО первый прогон уникального текста.** SQL Lab кэширует
  результат (16,42 → 1,57 с на одном тексте); самый первый за долгое время —
  холодное чтение с диска. Кэш ломается строкой `-- <метка>` в начале.
  Правку скорости доказывать контрольными суммами (см. §6).
- Типы: `Nullable(Array)` НЕ существует (заглушки — `CAST([], 'Array(String)')`);
  валидатор UI не ест кортежный CAST `CAST([], 'Array(Tuple(…))')` (лечится
  arrayFilter-формой); у Int64/UInt64 нет супертипа в массивах (скаляры CH
  мирит). UNION-плечи обязаны совпадать и по ШИРИНЕ, и по типам — Code 53
  ловит только бой; генераторы считают колонки плеч сами (check_arms в
  .gen_who.py).
- JOIN: Nullable-ключ в ON → Code 70 CANNOT_CONVERT_TYPE (лечение — сентинел
  `ifNull(toInt32OrNull(k0), toInt32(0))`); кортежи с массивом внутри не
  имеют супертипа (Code 386) — коллекции заводить `arrayMap(c -> (3,c), cn)`;
  колонки джойна в GROUP BY — только через any().
- Джиня: `where_in` НЕ экранирует обратный слэш (`DOMAIN\a.petrov` роняло
  запрос) — `{% set selq = [sel0|string|replace('\\','\\\\')]|where_in %}`;
  `|int` на мусоре даёт 0 (инъекция нейтрализуется); белые списки значений
  обязательны; фигурные скобки JSON в %-формате генератора экранировать `{%%`.
- Стенды НЕ исполняют SQL: jt сверяет рендеры между собой (обе стороны могут
  быть одной битой), vm гоняет JS на моках. Исполнимость видит только
  ClickHouse/SQL Lab. Урок v6→v7: CTE-цепочку портировать ТОЛЬКО байт-в-байт.
