# Proteus Adoption — интерактивный макет

Открыть: `index.html` двойным кликом. Интернет не нужен — ECharts лежит локально
в `vendor/`, шрифт Inter деградирует до системного, если Google Fonts недоступны.

## Что внутри

```
index.html          каркас + модалка «Как это устроено»
assets/app.css      дизайн-система: токены, компоненты, адаптив
assets/data.js      СИНТЕТИЧЕСКИЕ данные в структуре будущих SQL-датасетов
assets/ui.js        форматтеры чисел, подсказки, сборщики компонентов
assets/charts.js    конфиги ECharts — переносятся в Proteus почти дословно
assets/app.js       состояние, фильтры, вкладки, рендер
vendor/echarts.min.js  ECharts 5.5.1
_test.js            прогон всех состояний в Node: `node _test.js`
```

## Две вкладки — два вопроса

| Вкладка | На какой вопрос отвечает | Кому |
|---|---|---|
| **Отчёты** | Динамика просмотров и пользователей по моему отчёту / коллекции / всем отчётам владельца / подразделению; закрепляемость и частота — по тому же выбору | Владельцы отчётов (бизнесовые и технические), аналитики |
| **Аудитория отчёта** | Дошла ли до отчёта его целевая аудитория, кто не дошёл, кто закрепился | Заказчики бордов, владельцы |

Вкладки «Обзор» и «Покрытие компании» из первой версии убраны: обзор — это
тот же экран без выбора строки (сделан подшапкой «В разрезе»), а покрытие
компании — вопрос управления BI, а не владельца отчёта; покрытие целевой
аудитории конкретного отчёта живёт на вкладке «Аудитория».

## Как устроен главный экран

Левая таблица — «в разрезе чего смотрим». Подшапка переключает разрез:
**отчёты · коллекции · владельцы · подразделения · специализация**. Клик по
строке выбирает её для всей вкладки: карточки KPI, динамика справа, частота
и закрепляемость пересчитываются под выбор. Повторный клик снимает выбор —
и экран показывает весь Proteus. Это и есть главный кейс владельца отчёта:
«посмотреть динамику по своему отчёту или по группе своих отчётов».

## Архитектура данных

Одна вкладка — один датасет. Вкладка забирает его целиком, дальше всё
считается в браузере.

**Мгновенно, без запроса в базу:** период (все 4 грануляции лежат внутри),
переключение разреза, выбор отчёта/коллекции/владельца/подразделения,
переключение видов панели.

**Осталось серверным** (помечено значком пересчёта ⟳):
- комбинация фильтров по атрибутам сотрудников и отчётов — длинный формат
  не даёт *пересечения* двух разрезов сразу, для этого нужен широкий куб;
- поимённые списки аудитории — тянутся по выбранному отчёту;
- когорты выбранного отчёта — куб «отчёт × когорта × возраст» по всем
  отчётам в браузер не поедет (в бою доработка ноды: сейчас retention
  считается отдельным датасетом без `dashboard_id`).

Датасеты: `ds_overview` (динамика/KPI/частота/когорты Proteus, ~4,5 тыс. строк),
`ds_reports` (карточки отчётов + `rts`/`rfreq` и групповые двойники
`gkpi`/`gts`/`gfreq` — то же с `GROUP BY` коллекция|владелец), когорты отчёта
(запрос по одному отчёту), `ds_audience` (метаданные доступа, пофамильно,
первые визиты).

**Пользователи групп не аддитивны.** У коллекции/владельца «пользователей» —
это `COUNT(DISTINCT user_id)` по группе: человек, открывший три отчёта
коллекции, считается один раз. Поэтому строки таблицы не складываются в
ИТОГО — итог считается отдельным уникальным по всей выборке. Просмотры
складываются точно.

## Решения, которые стоит обсудить

**Когорты закрепляемости** повторяют механику «Закрепляемости 2.0» боевого
борда: строка — месяц первого визита, рядом размер когорты полосой, дальше
возраст, раскраска — дивергентная **от медианы столбца**, код перенесён из
боевого графика один в один (жёлтый ← белый → голубой; медиана и размах
шкалы считаются только по закрытым месяцам, медиана подписана в шапке
столбца). Незакрытый месяц — серым курсивом, как в бою. Отличие от боевого
одно: возраст начинается с **+1 месяца** (столбца «старт» нет — в нём всегда
100% и та же когорта, смотреть не на что). Для отчёта когорты считаются
по первому визиту в этот отчёт ⟳; без выбора — по Proteus.

**Целевая аудитория отчёта** определяется тремя способами и честно об этом
говорит плашкой над карточками:
- *точный список* — `allowed_logins` (поимённые права). Покрытие без допущений.
- *по AD-группам* — `ad_groups_dash` × состав групп из `mdm_employee_daily_proteus`.
- *широкая группа* (охват ≥30% численности, например `tableau_all_employees`) —
  долю покрытия **не показываем**: знаменатель не описывает, для кого делали
  отчёт. Разрезы при этом остаются: видно, кто фактически ходит.

**Подписи значений стоят у каждой марки** графиков динамики. Когда бакетов
много (30 дней), подписи разворачиваются вертикально и над марками
резервируется место — числа не прореживаются.

**Подсказки «Что видно в данных»** — пороговый отбор фактов, не языковая
модель. Порог назван внизу блока. Нет факта выше порога — плашки нет.

**Типографика** — потолок веса 700 (в дизайн-системе противоречие между
текстом «восьмисотого нет» и её же CSS). Правило записано в шапке `app.css`.

**Палитра серий** `#0f9d8f / #4361ee / #b5179e` проверена валидатором
dataviz: 5/5 PASS, `--pairs all`. Пастель дизайн-системы проверку не прошла.

## Проверено

- `node _test.js` — все состояния (вкладки, 4 периода, 5 разрезов, выбор
  отчёта/группы, кривая/когорты, широкая AD-группа): без исключений, NaN,
  `undefined`; оси от нуля; в когортах нет столбца «старт».
- Геометрия через CDP (`.render/check.js`, ширины 1280/1440/1600/1920):
  переполнений и наложений нет; текстовые колонки переносятся, когортная
  таблица при <1366px встаёт колонкой, а не в прокрутку.
- Числа сверены по DOM: KPI = ИТОГО частоты; «Дошли» = сумме первых визитов;
  ИТОГО групп меньше суммы строк (уникальные).
- Скриншоты состояний: `.render/shots/` (браузер запускается внешним
  `start-browser.sh`, см. память проекта).

**Не проверено:** поведение на ширинах <1240px глазами; типографика на
Windows (шрифтfallback).
