## Ответственность и противоречия

- Общий playbook — платформа, SQL/Superset, доступ/кэш, ETL, несколько чартов, песочница и поставка. Builder — устройство одного JS-чарта, шаблоны, validate/smoke, NOTES/FIELDS. Adoption — конкретная методология и принятые владельцем ограничения. [Раздел 4 playbook](../vendor/proteus-playbook/SKILL.md) перечисляет уточнения builder: viewport iframe, тултипы, ResizeObserver, ESLint, минификация и sandbox-стенд. Их нельзя заменять старым шаблоном без проверки.
- CLAUDE.md называет CONTEXT.md «живым статусом», но CONTEXT начинается сентябрём. Более поздние решения читаются в CLAUDE, NOTES и документации соответствующей поставки. Старые папки обновлений и `memory/` не удалены: это история, а не очередь невыполненных задач. `New Feedback` про «Мои борды» и смену логинов не считается новым заданием без сверки последующих исправлений.
- GP-поставка 2026-10-23 пока не применена по сообщению владельца. Замороженная папка актуального листа — база отката; `pack.py` по умолчанию уже нацелен на GP-поставку. Не запускать сборку вслепую.
- Playbook содержит исторические «2.0.1», но актуализированная таблица сообщает корпоративный форк 2.1.0 и sqlparse 0.4.3 + патч; имя `superset201.py` описывает модель пути. kit/RESULTS за 08.10 использует старое имя М1: по SKILL это теперь М0. Эти версии документированы, не измерены в живом Proteus в этом чате.
- В ClickHouse upstream есть внутренняя рассинхронизация: SKILL.md и metadata.json объявляют v0.4.0, а скомпилированный AGENTS.md всё ещё подписан v0.1.0. Для точной идентификации используется SHA, а для рекомендаций — SKILL.md и отдельные rules; устаревшую подпись не исправляли внутри побайтового импорта.
- ClickHouse upstream содержит рекомендации для более новых серверов: `parallel_hash` — default с 24.11, автоматический выбор правой стороны JOIN — 24.12+. Нельзя переносить их как гарантии 24.8. `agent-discovery-schema` предлагает `system.*`, а Proteus SQL Lab это запрещает; использовать разрешённые операции и подтверждённые метаданные. Навык не даёт разрешения подключаться к БД.
- **Неразрешённое противоречие по кэшу:** invariant 11 общего SKILL утверждает, что `cache_timeout=-1` не выключает кэш; инструкция GP-поставки Adoption (раздел настройки трёх датасетов, строки 724–726 исходного файла `0. Что куда и как проверить.md`) сообщает противоположный результат проверки: `-1` выключает, `0` наследует значение. Это разные документированные свидетельства о корпоративном форке. Не выбирать настройку по одному тексту и не считать её проверенной в текущем проде: отдельно проверить отсутствие/наличие cache hit в Network на тестовом борде после изменения и после обновления витрин.
- Web skill требует свежую сеть и WebFetch. В облаке можно использовать доступный HTTPS-клиент; при отсутствии доступа — закреплённый `command.md` с явным указанием режима. Не называть snapshot «последними правилами». Рекомендации Next/React применимы только если такой стек есть. Arial 400/700, особенности iframe и профиль Adoption в DESIGN_SYSTEM §16 сохраняются.
- `.stand/min.cjs` побайтово совпал с импортированным `kit/min.cjs`; это существующая копия, не второй источник правил. Новая доставка её не меняет. У builder есть собственные регрессионные fixtures, у playbook — модель борда: они дополняют, а не заменяют друг друга.
- Импортированные главы содержат примеры из других проектов, не доставляемые с playbook. Это ссылки на происхождение опыта, не зависимости запуска. Не создавать фиктивные файлы, чтобы сделать такие примеры «рабочими».

Один локальный запуск не называется RUM или замером SQL на проде. Мобильные
проверки и внешние аналитические сервисы здесь не применяются: владелец выбрал
ноутбуки/мониторы и корпоративный Proteus.

## Воспроизводимое обновление

Из корня checkout:

```bash
python3 tools/knowledge/check.py
python3 tools/knowledge/sync.py --check
python3 tools/knowledge/test_sync.py
# Повторная доставка ТОЧНО закреплённых файлов (требует GitHub):
python3 tools/knowledge/sync.py
# Обновить один источник на полный, заранее рассмотренный SHA:
python3 tools/knowledge/sync.py --update proteus <40-символьный-SHA-TeamPulse>
# source IDs: clickhouse, web-design, web-rules, proteus, anthropic-frontend, web-performance
python3 tools/knowledge/check.py
git diff --stat
```

Скрипт не использует локальные upstream-папки пользователя. Скачивает через Git, проверяет commit и hashes, не исполняет upstream install-скрипты и отказывается перетирать изменённые/посторонние файлы импорта, включая изменения во время скачивания. Симлинки запрещены; обычный Python-кэш `__pycache__/*.pyc` допускается и не импортируется. Восемь автономных тестов проверяют эти защиты, восстановление отсутствующих файлов и замену принадлежащих импорту файлов при обновлении. Обновление web skill и его rules — две отдельные версии, согласовать их при обновлении. После обновления пересмотреть аудит/совместимость и сценарии; закоммитить lock и файлы вместе. Общие исправления сначала в TeamPulse, затем импорт; локальные поправки поведения — в AGENTS/маршрутизаторе.

## Сценарии выбора и предел проверки

[scenarios.json](scenarios.json) содержит пять характерных запросов: ClickHouse, UX, кросс-фильтры, доступ/кэш, поставка. `check.py` проверяет, что их входы существуют и представлены в навигации, локальные файловые цели Markdown-ссылок новых материалов и корневой навигации разрешаются (якоря заголовков не проверяются), helpers/templates не потеряны, upstream hashes совпадают. Это проверка карты, а не симуляция автоматической активации или успешной работы SQL в проде. В kit/RESULTS.js.md есть два исторических примера Markdown-ссылки с целью `…`: это заглушки, а не файловые зависимости; checker исключает только эту точную пару файл/цель. Ссылки-примеры вне playbook и URL не объявляются проверенными сетевыми ресурсами.
