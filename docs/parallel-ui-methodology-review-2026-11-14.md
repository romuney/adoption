## Подтверждённые несовпадения обвязки на проверенном SHA

1. **Пустое значение аудитории отбрасывается транспортом.** `src/loader.js:23–28` требует `v.length > 0`. Но `SQL 7:201–204` сохраняет пустые значения `aud_spec_f`, `aud_stream_f`, `aud_hq_f`, `aud_it_f`; `SQL 5/7` сохраняют их и для `ca_hq_f`, `ca_it_f`. Исходный UI показывает такие группы как «— не указано». В браузерной песочнице с реальными SQL-фикстурами команда с правильными channel/id/session и `aud_hq_f:['']` не вызвала ни одной отправки фильтра; такая же команда с `['HQ']` вызвала одну. `main.values()` дополнительно склеивает пустой фильтр с выбором пустой строки.

2. **Ширина календаря берётся не из той области.** `pa-one.chart.js:3239`, `calLeftW()`, использует `window.innerWidth <= 760`. В едином iframe CSS уже переключается по ширине контейнера панели, но JS по ширине всего iframe. Возможен одноколоночный CSS с лишним вычитанием 304/364 пикселя в геометрии. Нужна точечная привязка расчёта к ширине панели. Глобально подменять `window.innerWidth` нельзя: fixed-подсказки и выпадающие окна измеряют настоящий viewport намеренно.

3. **Новый nonce на каждый emit препятствует повторному серверному cache hit.** `src/main.js:206–216` каждый раз меняет `pa_next_<owner>_req`, включённый в SQL-ответ и текст запроса. Защита от устаревших ответов нужна, но её цена не присутствовала в таком виде в старом макете. Полные локальные ответы следует хранить отдельно от транспортного ключа.

Первый дефект воспроизведён исполнением. Второй подтверждён несовместимыми ветвлениями CSS/JS и требует браузерной проверки после исправления. Третий следует из состава SQL и nonce; это не замер производительности реального Proteus.

## Контракт безопасного локального кэша

Кэш только в `window.__paNext`, в памяти текущего iframe/session; не localStorage, не общий серверный объект. Данные другого поколения не восстанавливать. Для переиспользования в иной сессии потребовался бы явный пользовательский ключ: каталог содержит `current_username()`, включая строку `me`.

Ключ строить из **точных отправленных business masks**, а не из lossy `flt/sj` echo. Структурный JSON фиксированного whitelist полей безопаснее `selectionKey()`. Включить часть датасета и поколение; версия приложения естественно ограничена жизнью iframe. Транспортные `pa_nonce` и `pa_next_*_req` не входят в business-key, но остаются обязательными при принятии сетевого ответа.

Минимальные доказанные нормализации для допустимых масок:

| Поле | Допустимая нормализация | Ограничение |
|---|---|---|
| `period_param` | Отсутствие/`[]` → `['d']` | Существующий массив сохранять точно; другие грануляции не объединять |
| `pub_f`, `act_f`, `exc_f` | Отсутствие/`[]` → `['1']` | `['0']` всегда отдельное состояние |
| `mode_param` | Отсутствие/`[]` → `['report']` **только если `sel_f` отсутствует или `[]`** | С непустым `sel_f` отсутствие режима игнорирует выбор, `report` применяет его |

Для базового сценария «всё → отчёт A → снять выбор» необходима именно условная нормализация режима. Нормализацию `['']`, неверных режимов и иных формально эквивалентных некорректных входов можно не вводить: дополнительный cache miss безопаснее неверного совпадения.

Не допускаются:

- Удаление пустых строк: `aud_hq_f:['']` и отсутствие фильтра имеют разный смысл.
- Удаление кавычек, слешей, CR/LF, trim или lower-case. `SQL 7 q():88–92` экранирует исходные строки; echo удаляет часть символов лишь для своей сериализации. Например `A"B` и `AB` могут быть разными реальными значениями с одинаковым echo.
- Ключ на основе склейки через запятую/точку с запятой: `['a,b']` и `['a','b']` коллидируют в существующем `selectionKey()`.
- Безусловные sort/dedup: скалярные фильтры используют `first`; `aud_head_f` проверяет `length == 1`.
- Объединение `sel_f:['0']` с пустым выбором.
- Вычисление мультивыбора суммой preview одиночных отчётов: уникальные люди пересекаются.
- Подмена nonce старого сетевого ответа новым и выдача его за новый ответ. Локальное восстановление должно быть отдельным доверенным путём с доказанным совпадением business-key.

Очередь и отображение требуют отдельного согласования. Правильный полный ответ на уже отправленный B должен освободить очередь, даже если пользователь успел выбрать A и видит preview A. Безусловно отклонять такой ответ по последнему **ещё не отправленному** intent нельзя. При локальном восстановлении A нельзя незаметно потерять подтверждение B; guard исходного рендерера также не должен ждать новый сетевой nonce для уже доказанного локального ответа.

## Проверки после реализации

Требуется повторная независимая проверка кода и браузерные сценарии: «всё → полный A → снять»; «полный A → preview B → A до debounce»; сброс во время запроса B; повтор полного ответа; смена d/w/m/q и обратно; смена фильтров людей/ЦА; пустой атрибут; изменение поколения; неверный nonce; несколько выбранных отчётов. Числа и содержимое детальных вкладок после restore должны совпадать с полным SQL-ответом для того же business-key. Проверка только статуса `ready` недостаточна.

Доступ к реальному GP/Proteus для этого аудита не использовался. Сходство синтетического макета, происхождение JS и корректность модели SQL — разные уровни доказательства; один не заменяет другой.

## Повторная проверка новой обвязки в тот же день

После реализации кэша и очереди проведён независимый review. Новые business-key используют структурный JSON точных отправленных масок, условный default `mode_param`, отдельные session/generation/part. Транспортный ledger связывает nonce с отправленной маской; lossy echo не служит ключом кэша. Исходные виджеты, SQL 3/5/7 и актуальный ETL по Git не менялись.

В первой реализации дополнительно обнаружены и исправлены:

- При суммарном размере baseline и нового ответа свыше лимита 24 MiB вытеснялся именно новый ответ; он не мог попасть на экран. Теперь сохраняется последний валидный ответ, при необходимости уступает baseline.
- При переходе начального `generation=''` в готовую загрузку ledger сохранял пустое поколение и отклонял все правильные ответы. Теперь сброс происходит при любой смене поколения, включая пустое.
- После подтверждённой ошибки отправки delayed `HELLO` автоматически повторял команду, хотя периодический resend был остановлен. Теперь автоматические повторы подавлены и для этой ветки; доступна явная кнопка повтора. Её реальная кликабельность проверена в браузере.
