## Предложения по приоритету

### P1. Не терять смысл чисел при полном скролле

**Изменение:** в существующий подзаголовок Dynamics и Who добавить компактный применённый период; во всплывающем пояснении — границы сравнения, дату данных и условия расчёта. Не добавлять закреплённую шапку. Для вкладок с другими временными правилами показывать их собственный смысл: календарь уже подписывает свои 60 дней в проверенном режиме, закрепляемость не должна выглядеть отфильтрованной верхним периодом, MAU остаётся за последний закрытый календарный месяц. Нельзя механически проставить один диапазон всем вкладкам.

**Найдено и уже исправлено:** шаг «Показатели» ранее говорил «Эти показатели относятся к текущему периоду…», хотя в `Виджеты/pa-one.chart.js:2932` подсказка MAU прямо говорит, что он от периода в шапке не зависит. Основной исполнитель уточнил текст в `Параллельный отчёт — pa_next/src/interaction.js:183`: «Большинство — за выбранный период; MAU — за последний закрытый календарный месяц». Это исправление описания, не формулы; оно больше не относится к оставшимся пробелам.

**Данные:** уже есть в состоянии и модели. Новый SQL не нужен. Подпись должна относиться к отображаемому ответу, а не к ещё не завершившемуся выбору: старые числа с подписью нового периода недопустимы.

**Проверка результата:** после полного скролла и скрытия каталога пользователь определяет область и период без возврата наверх; при быстрых выборах подпись не опережает данные; MAU, ритм и когорты сохраняют свои временные правила. На узком экране подпись не увеличивает высоту панели и не сдвигает вкладки.

### P1. Дать следующий шаг из наблюдения

**Изменение:** в раскрытом наблюдении разместить одно подходящее действие. Например, при изменении пользователей — «Проверить по дням» с переходом в календарь; при малой доле постоянных — «Посмотреть частоту» с переходом в существующий режим «Кто смотрит». При переходе сохранять область и период. Если переход ведёт в закрепляемость, явно сохранить её независимость от периода.

Текст действия должен обещать проверку, а не объяснение причины. «Пользователи не вернулись» нельзя автоматически превращать в «у пользователей проблема с отчётом». Не обещать поимённый список ушедших, пока его доступность не подтверждена для соответствующей модели: имеющееся агрегированное число не гарантирует список.

**Данные:** готовые вкладки и существующие числа. Новая методология не нужна; потребуется аккуратная навигация и тест текущей фильтрации. Для наблюдений по всей области нельзя незаметно применять локальный список людей, с которым факт не рассчитан.

**Проверка результата:** из конкретного факта пользователь за одно действие попадает в подходящую проверку; область не расширяется и не сужается без явного выбора; заголовок объясняет, что проверяется. В отсутствие готовых данных действует нынешняя единая область загрузки.

### P2. Копировать результат вместе с условиями

**Изменение:** по запросу копировать краткую текстовую сводку: выбранная область и ID отчётов, период и сравнение, дата данных, применённая ЦА и исключения, используемый режим/сегмент. Для значений MAU отдельно указывать его месяц. Существующее копирование табличных строк сохранить; не вставлять служебные строки в TSV так, чтобы ломалась вставка в Excel.

Это отдельная функция от уже существующего копирования ссылки на исходный отчёт. Не обещать восстановление состояния по URL без проверки возможностей Proteus. Не добавлять серверное сохранение персональных данных и автоматическую рассылку.

**Данные:** текущие применённые условия и отображаемая модель. Новый SQL не нужен. Для состояния с ошибкой или незавершённой загрузкой нельзя выдавать сводку как подтверждённый результат нового выбора.

**Проверка результата:** коллега может повторить анализ по сводке; период, ЦА, область и исключения совпадают с выгрузкой. В текст не попадает не применённый черновик фильтров; скопированный объём людей соответствует существующему режиму экспорта.

### P2. Дополнить «Как работать» маршрутами задач

**Изменение:** внутри существующего гида дать три коротких маршрута: «Проверить свой отчёт», «Разобрать изменение», «Найти недошедшую ЦА». Маршруты должны показывать уже имеющиеся действия и объяснять ожидаемый итог; не нужно добавлять новые постоянные кнопки или автоматическую оценку качества отчёта.

**Данные:** имеющиеся функции. Для «Моих отчётов» учитывать, что кнопка зависит от распознанного пользователя; при её отсутствии маршрут начинается с поиска владельца. Не менять фильтры и не сбрасывать выбор без явного действия пользователя.

**Проверка результата:** новый пользователь завершает сценарий и может объяснить, какую область изучил, какой факт получил и какой следующий шаг выбран. Это следует подтвердить коротким наблюдением за пользователем; экспертный обзор не заменяет такую проверку.

## Краткий комментарий владельцу

Данных и инструментов уже достаточно для большинства разборов. Больше всего не хватает трёх вещей: видеть период после скрытия шапки, переходить из наблюдения прямо к подходящей проверке и копировать результат вместе с условиями расчёта. Затем полезно превратить часть гида в три рабочих сценария. Новые показатели для этого не нужны; методология и числа сохраняются. Оценку бизнес-ценности и эффекта внедрения стоит делать только после появления соответствующего контекста, а не выводить из числа просмотров.
