# Параллельный Proteus Adoption: требования и приёмка

Сводка запросов владельца от 2026-11-13. Рабочая ветка `new`.

## Результат

1. Подключить ClickHouse Best Practices, Web Design Guidelines, Proteus Playbook и локальный builder с воспроизводимой доставкой знаний, аудитом и навигацией. Сохранить коммит в GitHub.
2. Подготовить **новый параллельный отчёт**, отдельная папка `Параллельный отчёт — pa_next/`, без изменения существующего отчёта и старых поставок.
3. Дать самостоятельный YAML ноутбука Helicopter: только необходимые исходники, преобразования и выгрузки финальных ClickHouse-таблиц. Не запускать старые лишние параграфы и не требовать предварительного запуска старого ноутбука.
4. Все создаваемые/изменяемые объекты GP и ClickHouse имеют новый префикс `pa_next_`, включая промежуточные и временные таблицы. Читать общие корпоративные источники можно; изменять старые таблицы нельзя. Новый ноутбук не обновляет кэш или метаданные старого отчёта.
   Уточнение владельца: новые GP-таблицы создавать без физического префикса `usr_cross_data.`, в рабочей/временной схеме Helicopter; экспорт использует те же короткие имена. Заголовки всех параграфов должны по-русски объяснять выполняемое действие, без `PA NEXT` и имени таблицы вместо описания.
5. Поставка включает SQL датасетов, JS чартов, CSS, JSON направлений кросс-фильтрации, инструкцию создания новых объектов и диагностику. Идентификаторы новых объектов подставляет владелец; автоматических изменений прода нет.
6. Предпочтительная архитектура: один видимый чарт со всем интерфейсом; вспомогательные чарты параллельно загружают данные. Скрытые загрузчики должны оставаться смонтированными. Без обязательного слияния всех данных в один тяжёлый SQL.
7. Оптимизация GP/ClickHouse и UX разрешена, но **сходимость цифр и сохранение методологии важнее ускорения**. Не обещать ускорение без сопоставимого замера.
8. Работа автономная, с независимыми критиками, повторными проверками и исправлениями. Коммит и отправка в `new` разрешены. Публикация облачной среды не запрашивалась и не выполняется.

## Инварианты

- Отбор просмотров, границы дат, исключения служебных событий и нормализация логинов соответствуют актуальному YAML. Каждое изменение выражения требует сравнения на пограничных данных.
- Уникальных пользователей/логины нельзя суммировать по отчётам или периодам; дедупликация сохраняется.
- Готовые периоды 30 дней/20 недель/12 месяцев/8 кварталов и произвольные периоды сохраняют границы окна, неполные периоды и алгоритм предыдущего периода.
- MAU, динамика, частота, когорты, каталог и аудитория согласованы. Признаки доступа, целевая аудитория, знаменатели и ограничение текущим пользователем не меняются ради скорости.
- Шапка влияет на каталог и панель; каталог — на панель; выбор людей в панели — на каталог. Самовлияние выключено. Передача всех фильтров всем загрузчикам недопустима.
- Устаревшие ответы, потерянные сообщения, повторы, разные фильтры/версии данных не должны приводить к смешению показателей. Неготовность отображается явно; отсутствие ответа не означает ноль.
- Неполная выгрузка не объявляется готовой. Метод маркировки поколения и его ограничения фиксируются; набор последовательных выгрузок не называется атомарной транзакцией.
- Прежние продовые файлы не изменяются. Старые таблицы не очищаются и не перезаписываются. Общие корпоративные источники read-only.

## Проверки до передачи

| Проверка | Критерий |
|---|---|
| Доставка знаний | Три навыка, полные helpers, закреплённые SHA/hashes, локальные ссылки, пять сценариев маршрутизации, повторная доставка из Git |
| YAML | Парсинг, только зависимые параграфы, валидные Python/SQL, все записываемые имена из отдельного namespace, отсутствие старых side effects |
| Числа | Строгое сравнение полного результата старого и нового расчёта на одних данных. **Любая ошибка SQL — провал**, даже одинаковая с обеих сторон; списки/когорты сравниваются, не только итоговый KPI |
| Актуальная методология | Отдельные кейсы на фильтрацию просмотра из нового YAML и границы времени, отсекаемые события и логины |
| UI/канал | Browser-сценарии выбора, ответов в разном порядке, устаревших/потерянных сообщений, смены поколения, ошибок, повторов и ресайза; проверка направлений emit |
| UX | Явные загрузка/ошибка/пустое состояние, доступные контролы, отсутствие наложений, совпадение слов и цифр; Arial и ограничения Proteus |
| Производительность | Сопоставимые данные, фильтры, версия CH и число потоков; отдельно холодное/тёплое. Не переносить синтетические секунды на прод без оговорки |
| Воспроизводимость | Генератор даёт тот же результат; инструкция содержит порядок создания новых объектов, замену id, проверки и остановку при расхождении |
| Независимый review | Проверка изоляции и методологии отдельно от автора; найденные блокеры исправлены или явно оставлены как препятствие готовности |

## Граница подтверждения

Локальная модель Superset/ClickHouse и PostgreSQL не подтверждает особенности корпоративного форка, Greenplum, Helicopter API, права доступа и реальное время в проде. Поставка может быть готова к **контролируемому тесту рядом с продом**, но не считается принятой или безопасной для замены старого отчёта без проверок владельца. В инструкции должны быть предварительные проверки коллизий имён и последовательность остановки/отката; старый отчёт продолжает работать.
