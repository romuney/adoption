# Флоу n8n `ta_save` — как собрать настоящий

Инструкция для сборки боевого флоу из макета. Макет `n8n/ta_save.mock.json`
импортируется и работает сразу: вызовы Trino в нём — заглушки с мок-ответами.
Чтобы сделать его боевым:

1. создать таблицу в DLH (§2);
2. импортировать `n8n/trino_query.json` — подпроцесс, который выполняет один SQL в Trino;
3. в `ta_save.mock.json` заменить 4 ноды `Trino: …` на **Execute Workflow →
   trino_query** (§4);
4. вписать имена таблиц и колонок в ноду **«Конфиг и валидация»** — это
   единственное место с именами;
5. прогнать кейсы из §6 и передать мне то, что перечислено в §7.

Остальные ноды (валидация, проверки, сборка SQL, ответы) — готовая логика,
менять их не нужно.

---

## 1. Решения, на которых всё стоит

| Вопрос | Решение |
|---|---|
| Кто вызывает | Логин берём из Proteus: при авторизации он подставляет `user_name`, и UI кладёт его в `login` запроса. Флоу ему доверяет. |
| Кто может сохранять | **Все владельцы отчёта** и только они. Отдельных админов нет. |
| Что храним | Условия **названиями** — ровно те значения, что выбраны в фильтрах конструктора. Люди не хранятся. |
| Разрезы | `lvl3`, `lvl4`, `stream`, `spec`, `exp`, `it`, `hq`, `adgroup`. Поимённых списков нет. |
| Логика условий | Внутри разреза ИЛИ, между разрезами И, пустой разрез не ограничивает — как в конструкторе. |
| Хранилище | DLH на Trino, журнал событий: только дописываем, каждая запись — новая версия. |
| В ClickHouse | Ноутбук `notebooks/ta_sync_clickhouse.py` раз в 15–30 минут. |

Про логин без проверки: кто знает адрес webhook, может отправить запрос с
чужим логином. Это осознанное допущение. Каждая запись подписана `saved_by`,
так что подмену видно в журнале. Если понадобится строже — включить в
Webhook-ноде `Authentication: Header Auth` или пускать запросы только с хоста
Proteus.

## 2. Таблица в DLH

```sql
CREATE TABLE <catalog>.<schema>.ta_event (
  event_id      VARCHAR,          -- '<request_id>-v<version>'
  request_id    VARCHAR,          -- генерирует UI; повтор не создаёт новую версию
  dashboard_id  BIGINT,
  action        VARCHAR,          -- 'save' | 'deactivate'
  version       INTEGER,          -- 1, 2, 3… на отчёт; растёт и на deactivate
  f_lvl3        ARRAY(VARCHAR),   -- условия: названия, как в фильтрах
  f_lvl4        ARRAY(VARCHAR),
  f_stream      ARRAY(VARCHAR),
  f_spec        ARRAY(VARCHAR),
  f_exp         ARRAY(VARCHAR),
  f_it          ARRAY(VARCHAR),
  f_hq          ARRAY(VARCHAR),
  f_adgroup     ARRAY(VARCHAR),
  audience_cnt  INTEGER,          -- человек под условиями в момент сохранения; NULL у deactivate
  comment       VARCHAR,          -- «для кого отчёт», необязательно
  saved_by      VARCHAR,          -- логин из Proteus, нижний регистр
  saved_at      TIMESTAMP(6) WITH TIME ZONE,
  client        VARCHAR           -- 'proteus_adoption_ui'
)
WITH (format = 'PARQUET');
```

Текущая ЦА отчёта — запись с максимальной `version`. Если это `deactivate`,
ЦА у отчёта нет.

Учётке, под которой n8n ходит в Trino, нужны: `SELECT` + `INSERT` на
`ta_event`, `SELECT` на таблицу владельцев, mdm и членство в AD-группах.

## 3. Контракт webhook

`POST /webhook/proteus/ta`, тело JSON:

```json
{
  "action": "save",
  "login": "a.petrova",
  "request_id": "6f1c2a9e-…",
  "dashboard_id": 14037,
  "expected_version": 2,
  "filters": { "lvl3": ["Блок «Розница»"], "spec": ["Аналитик", "Менеджер продукта"] },
  "comment": "Отчёт для аналитиков и продактов розницы"
}
```

| Поле | Правило |
|---|---|
| `action` | `save` или `deactivate` (у `deactivate` нет `filters`) |
| `login` | `user_name` из Proteus; `[A-Za-z0-9._-]`, сравнивается в нижнем регистре |
| `request_id` | uuid от UI, 8–64 символа `[A-Za-z0-9-]` |
| `expected_version` | версия, которую человек видел на экране; `0`, если ЦА ещё не было |
| `filters` | ключи только из списка разрезов; хотя бы одно условие; ≤ 200 значений на разрез |

Ответы:

| Код | `error` | Когда |
|---|---|---|
| 200 | — | `{ok, action, dashboard_id, version, saved_by, saved_at, audience_cnt, sync: "scheduled"}` |
| 200 | — | повтор `request_id`: `{ok, replay: true, version, …}` — новой строки нет |
| 400 | `bad_action` · `bad_dashboard_id` · `bad_request_id` · `bad_expected_version` · `unknown_dims` · `bad_values` · `too_many_values` · `no_conditions` · `bad_comment` | запрос кривой |
| 401 | `no_login` | логин не пришёл |
| 403 | `not_owner` | не владелец; в `detail.owners` — кто владелец (UI покажет, к кому идти) |
| 404 | `report_not_found` | у отчёта нет владельцев в таблице владельцев |
| 409 | `version_conflict` | пока человек редактировал, другой владелец сохранил; в `detail` — текущая версия и кто |
| 409 | `nothing_to_deactivate` | снимать нечего |
| 422 | `unknown_values` | значения нет в текущей структуре (переименовали); в `detail` — какие |
| 422 | `empty_audience` | под условия никто не попадает |

## 4. Ноды по порядку

Схема: каждая нода передаёт дальше объект `{ok, cfg, DIMS, req, ctx}`. Нода
`SQL: …` добавляет к нему `sql`. Нода `Trino: …` возвращает только `{rows,
update_count}`: так ведёт себя Execute Workflow, поэтому следующая нода
забирает контекст через `$('SQL: …')`. Значит, замена заглушки на Execute
Workflow ничего не ломает ниже по цепочке.

| # | Нода | Что делает |
|---|---|---|
| 1 | **Webhook** | `POST proteus/ta`, ответ из ноды Respond |
| 2 | **Конфиг и валидация** | `cfg` с именами таблиц/колонок (**вписать здесь**); проверка по §3; канонизация условий (без дублей, отсортировано) |
| 3 | IF «Запрос корректен?» | нет → ошибка |
| 4 | **SQL: владельцы** | `SELECT DISTINCT lower(owner_login) … WHERE dashboard_id = …` |
| 5 | **Trino: владельцы** | → Execute Workflow |
| 6 | **Проверка: владелец?** | пусто → 404; логина нет в списке → 403 |
| 7 | IF «Владелец?» | |
| 8 | **SQL: текущая версия** | последняя версия отчёта + поиск того же `request_id` одним запросом |
| 9 | **Trino: текущая версия** | → Execute Workflow |
| 10 | **Сверка версии** | повтор `request_id` → 200 с прежним; `expected_version` ≠ текущей → 409 |
| 11 | IF «Версия совпала?» | |
| 12 | IF «Это save?» | `deactivate` сразу идёт на шаг 17 |
| 13 | **SQL: значения и численность** | какие из выбранных значений есть в mdm на последнюю дату + `count(*)` под условиями; один запрос через `UNION ALL` |
| 14 | **Trino: значения и численность** | → Execute Workflow |
| 15 | **Проверка условий** | нет значения → 422 `unknown_values`; 0 человек → 422 `empty_audience` |
| 16 | IF «Условия валидны?» | |
| 17 | **SQL: запись события** | **условный** `INSERT … SELECT … WHERE max(version) = expected AND request_id новый` |
| 18 | **Trino: запись события** | → Execute Workflow |
| 19 | **Проверка записи** | `update_count ≠ 1` → 409 (кто-то записал между шагами 9 и 18) |
| 20 | Ответ: 200 / Тело ответа: ошибка → Ответ: ошибка | наружу уходят только `error` и `detail`, без `sql` и `cfg` |

### Замена заглушки на Execute Workflow

Для каждой из 4 нод `Trino: …`:

- тип **Execute Workflow**, Source: Database, Workflow: `trino_query`;
- режим — по одному item (`Run once for each item`), вход — текущий item с полем `sql`;
- **имя ноды оставить прежним**: следующие ноды на него не ссылаются, но так
  читается проще. Ссылки `$('SQL: …')` идут на ноды SQL, их не трогать.

Подпроцесс `trino_query` ходит в Trino REST (`/v1/statement`) и ждёт ответа.
Подключение берёт из переменных окружения n8n: `TRINO_URL`, `TRINO_USER`,
`TRINO_PASSWORD`, `TRINO_CATALOG`, `TRINO_SCHEMA`. Если у вас в n8n к Trino уже
ходят по-другому (своя нода, шлюз), используйте его. Главное — сохранить
выход: `{ rows: [{колонка: значение}], update_count }`. Для INSERT
`update_count` — число вставленных строк.

### Что вписать в «Конфиг и валидация»

```js
T_EVENT:   'таблица из §2',
T_OWNERS:  'таблица владельцев отчётов: dashboard_id, owner_login',
T_MDM:     'mdm_employee_daily_proteus',
T_ADGROUP: 'членство в AD-группах: login, group_nm',
MDM_LOGIN: 'колонка логина в mdm',
MDM_DT:    'колонка даты среза в mdm',
DIM_EXPR:  { lvl3: 'e.<колонка>', … }   // разрез → выражение, дающее ТО ЖЕ название, что в фильтре
```

`DIM_EXPR` — главное место, где можно ошибиться. Выражение должно давать
строку, совпадающую со значением в фильтре конструктора побуквенно. Иначе
каждое сохранение будет падать с 422 `unknown_values`. Стаж (`exp`) и флаги
`it`/`hq` уже записаны выражениями `CASE`, подставить только имена колонок.
Если колонки называются иначе, чем `owner_login` и `group_nm`, поправить их
в нодах `SQL: владельцы` и `SQL: значения и численность`.

## 5. Ноутбук `ta_sync`: DLH → ClickHouse

`notebooks/ta_sync_clickhouse.py`, по расписанию раз в 15–30 минут. Каждый
запуск полностью пересобирает таблицы: событий сотни, инкремент не нужен.

1. Читает весь `ta_event` из Trino.
2. По отчёту берёт последнюю версию. `deactivate` → отчёт выпадает. Две
   записи одной версии (два владельца нажали «Сохранить» в одну секунду):
   побеждает более поздняя, в лог пишется предупреждение.
3. Сверяет значения со свежим mdm. Пропавшие (подразделение переименовали)
   кладёт в `stale_values`, ставит `ta_status = 'stale'`. ЦА не удаляет —
   владелец увидит пометку и пересохранит.
4. Считает `audience_cnt_now` — сколько человек в ЦА сегодня.
5. Перезаливает `adoption.ta_current` и `adoption.ta_event` через временную
   таблицу и `EXCHANGE TABLES`: отчёт не видит полупустую таблицу.

Имена таблиц и `DIM_EXPR` в ноутбуке — **те же, что в конфиге флоу**: и тот, и
другой отбирают людей одинаково.

## 6. Проверка перед сдачей

| Кейс | Ожидание |
|---|---|
| владелец, первое сохранение, `expected_version: 0` | 200, `version: 1`, строка в `ta_event` |
| тот же запрос ещё раз (тот же `request_id`) | 200, `replay: true`, новой строки нет |
| второй владелец сохраняет поверх, `expected_version: 1` | 200, `version: 2` |
| не владелец | 403, в DLH ничего |
| `expected_version` устарела | 409, в `detail` текущая версия и `saved_by` |
| `filters: {"logins": […]}` | 400 `unknown_dims` |
| `filters: {}` | 400 `no_conditions` |
| значение с апострофом (`O'Neil`) | сохраняется как есть, SQL не ломается |
| несуществующее подразделение | 422 `unknown_values` |
| условия, под которые никто не попадает | 422 `empty_audience` |
| отчёта нет в таблице владельцев | 404 |
| `deactivate` владельцем | 200; после запуска ноутбука отчёта нет в `ta_current` |
| Trino недоступен | ответ не 200 (n8n отдаст 500) |

В макете все кейсы уже проходят на мок-ответах. Там тестовые владельцы
`a.petrova` и `d.sokolov`, у отчёта `14037` уже есть v2, значения на
«Старое…» считаются исчезнувшими, на «Пустой» — дают ноль человек.

## 7. Что передать мне после сборки

Встраивание в отчёт (датасеты, UI, ноутбук) за мной. Для этого нужны:

1. **Полное имя `ta_event`** в Trino (`catalog.schema.table`).
2. **Таблица владельцев**: имя и колонки (`dashboard_id`, логин владельца).
3. **mdm**: имя таблицы, колонки логина и даты среза, колонки для каждого
   разреза — то, что вписали в `DIM_EXPR`.
4. **Членство в AD-группах**: имя таблицы и колонки.
5. **URL webhook** — его будет вызывать UI.
6. Куда кладём в ClickHouse (база `adoption` или другая) и где запускать
   ноутбук по расписанию.
7. Если что-то пришлось сделать иначе, чем здесь (поля, коды ответов), —
   список отличий.

Дальше с моей стороны:

- ноутбук: подставить имена, прогнать вхолостую (`TA_SYNC_DRY_RUN=1`), потом с записью;
- датасеты: в `ds_reports` — статус ЦА у отчёта (для пометки и фильтра), в
  `ds_audience` — отбор людей по утверждённой ЦА (PLAN.md §5.1);
- UI: три источника ЦА, кнопки сохранения и снятия, пометка в каталоге (PLAN.md §5.2–5.3).
