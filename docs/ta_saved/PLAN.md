# Утверждённая ЦА отчёта — план внедрения

Владелец отчёта собирает в конструкторе ЦА по атрибутам и структуре и
фиксирует: «это целевая аудитория моего отчёта». Дальше:

- вкладка «Аудитория» **по умолчанию** считает охват по утверждённой ЦА, а не
  «как роздан доступ»;
- отчёты с утверждённой ЦА **помечены** в каталоге, и по этой пометке можно
  отфильтровать;
- сохраняет **только владелец**. Это проверяет n8n, а не браузер.

Путь данных:

```
UI (конструктор) ──POST──▶ n8n webhook ──▶ DLH: proteus_adoption.ta_event (append-only)
                                                         │
                                       ноутбук ta_sync (по расписанию / по пинку от n8n)
                                                         ▼
                                   ClickHouse: adoption.ta_current (+ ta_event)
                                                         │
                              ds_reports (пометка) · ds_audience (люди ЦА) ◀── отчёт
```

Файлы рядом:

| Файл | Что это |
|---|---|
| `n8n/ta_save.mock.json` | Импортируемый в n8n макет флоу. Все внешние вызовы — Code-ноды `STUB · …` с мок-данными и контрактом в заметке ноды. Модель, которая собирает настоящий флоу, заменяет только их. |
| `notebooks/ta_sync_clickhouse.py` | Ноутбук (jupytext, `# %%`): DLH → ClickHouse, атомарная перезаливка. |
| этот файл | решения, схемы, логика отчёта, этапы, открытые вопросы |

## 1. Что именно сохраняем

**Только условия, не людей.** Разрезы — ровно те, что уже есть в конструкторе
(`AUD_DIMS` в `assets/data.js`):

| Ключ | Разрез | Хранить как |
|---|---|---|
| `lvl3` | Управл. структура, ур. 3 | **код** подразделения + имя-снимок |
| `lvl4` | Управл. структура, ур. 4 | **код** подразделения + имя-снимок |
| `stream` | Стрим | код, если есть в mdm, иначе имя |
| `spec` | Специализация | код, если есть, иначе имя |
| `exp` | Стаж | фиксированные бакеты (`lt1`, `1_3`, `3_5`, `5_10`, `10p`) |
| `it` | IT / non-IT | `it` / `non_it` |
| `hq` | HQ / non-HQ | `hq` / `non_hq` |
| `adgroup` | AD-группа | имя группы (это и есть её ключ) |

Почему коды: подразделения переименовывают. ЦА, сохранённая по имени «Блок
«Розница»», после ребрендинга блока молча станет пустой. Имя храним рядом
снимком — чтобы показать «было: …», если код исчез из справочника.

Семантика та же, что в конструкторе сейчас: внутри разреза — ИЛИ, между
разрезами — И, пустой разрез не ограничивает.

**Чего не сохраняем:** поимённых списков, поиска по логину, «только
тим-лиды». AD-группа остаётся — это атрибут сотрудника в mdm, а не список,
который ведёт владелец. ЦА пересчитывается каждый день по свежему mdm: пришёл
новый аналитик в блок — он сразу в ЦА.

**Единица сохранения — один отчёт** (`dashboard_id`). Сохранение доступно,
когда в области ровно один отчёт. Пакетное «на всю коллекцию» — во второй
итерации (это просто N событий с одним `request_id`, схема это уже держит).

## 2. DLH: журнал событий `proteus_adoption.ta_event`

Append-only: в DLH-таблицы (Iceberg/Hive) дешевле дописывать, чем обновлять,
и бесплатно получается история версий и аудит. Текущее состояние =
последнее событие по `dashboard_id`.

| Поле | Тип | Смысл |
|---|---|---|
| `event_id` | string (uuid) | ключ события |
| `request_id` | string | идемпотентность: повтор того же запроса не создаёт версию |
| `dashboard_id` | bigint | отчёт |
| `action` | string | `save` · `deactivate` |
| `version` | int | 1, 2, 3… на отчёт; растёт и на `deactivate` |
| `f_lvl3` … `f_adgroup` | array<string> | условия, коды (8 колонок) |
| `filters_json` | string | те же условия каноническим JSON (отсортировано) — для отладки и UI |
| `labels_json` | string | `{код: имя}` на момент сохранения |
| `audience_cnt` | int | сколько человек попало под условия при сохранении |
| `access_cnt` | int | у скольких из них был доступ к отчёту |
| `comment` | string | «зачем такая ЦА», необязательный |
| `saved_by` | string | логин **из проверенной идентичности**, не из тела запроса |
| `saved_at` | timestamp | время n8n |
| `client` | string | `proteus_adoption_ui` / `api` |

Партиционирование не нужно: событий будут сотни в год.

## 3. n8n: флоу `ta_save`

Один webhook, два действия: `save` и `deactivate`. Читает UI не через n8n,
а из ClickHouse — через обычные датасеты (раздел 5).

### Запрос

```json
POST /webhook/proteus/ta
{
  "action": "save",
  "request_id": "6f1c…",
  "dashboard_id": 14037,
  "expected_version": 2,
  "filters": { "lvl3": ["ORG_RETAIL"], "spec": ["analyst", "pm"] },
  "comment": "Отчёт для аналитиков и продактов розницы"
}
```

`expected_version` — версия, которую человек видел на экране (0 — ЦА ещё не
было). Оптимистичная блокировка: два владельца не затрут друг друга молча.

### Шаги и ответы

| # | Нода | Ошибка → ответ |
|---|---|---|
| 1 | Webhook | — |
| 2 | Валидация: `action`, `dashboard_id`, `request_id`; ключи `filters` только из белого списка; хотя бы одно условие; ≤ 200 значений на разрез | `400 bad_request` |
| 3 | **STUB · Кто вызывает** — логин из проверенного источника (см. §7, вопрос 1) | `401 unauthenticated` |
| 4 | **STUB · Владельцы отчёта** — owners из метаданных Proteus | `404 report_not_found` |
| 5 | Проверка: логин ∈ владельцы (+ белый список админов, если решим) | `403 not_owner` |
| 6 | **STUB · Текущая версия** — последнее событие по отчёту в DLH; заодно ищем `request_id` | повтор `request_id` → `200` с прежним результатом |
| 7 | Сверка `expected_version` | `409 version_conflict` + текущая версия и кто сохранил |
| 8 | **STUB · Справочники mdm** — все ли коды существуют; сколько людей попадает; у скольких есть доступ | неизвестный код → `422 unknown_values`; 0 человек → `422 empty_audience` |
| 9 | Сборка строки события | — |
| 10 | **STUB · Запись в DLH** | `502 storage_failed` |
| 11 | **STUB · Пинок синхронизации** (запуск ноутбука вне расписания) — ошибка не роняет ответ | — |
| 12 | Ответ `200 {version, saved_at, audience_cnt, access_cnt, sync: "queued"}` | — |

`deactivate` идёт тем же путём, пропуская шаг 8.

Рекомендация к настоящему флоу: шаги 6→10 — одна транзакция или хотя бы
«вставить, если `max(version) = expected_version`» одним SQL, иначе гонка
между шагом 6 и 10 остаётся.

## 4. Ноутбук `ta_sync`: DLH → ClickHouse

Таблица маленькая (сотни строк), поэтому никаких инкрементов: каждый запуск
**полностью** пересобирает текущее состояние и подменяет таблицу атомарно
(`INSERT` во временную → `EXCHANGE TABLES`). Читатель никогда не видит
полупустую таблицу.

Что делает:

1. Читает `ta_event` целиком.
2. Последнее событие на `dashboard_id`; `deactivate` → отчёт выпадает из текущих.
3. Сверяет коды со **свежим** mdm: исчезнувшие складывает в `stale_values`,
   ставит `ta_status = 'stale'`. ЦА не удаляем — сигналим владельцу.
4. Пересчитывает `audience_cnt_now` (сколько человек ЦА сегодня) — чтобы в
   каталоге было видно, что ЦА «усохла» после реорганизации.
5. Перезаливает `adoption.ta_current` и зеркало `adoption.ta_event`.
6. Проверки: число отчётов в ClickHouse = числу активных в DLH; нет дублей
   `dashboard_id`.

Запуск: по расписанию раз в 15 минут **и** пинком из n8n после сохранения.
Если пинок недоступен — только расписание, и UI честно пишет «появится у
всех в течение 15 минут».

### ClickHouse

```sql
CREATE TABLE adoption.ta_current (
  dashboard_id      UInt64,
  version           UInt32,
  ta_status         LowCardinality(String),   -- active | stale
  f_lvl3            Array(String),
  f_lvl4            Array(String),
  f_stream          Array(String),
  f_spec            Array(String),
  f_exp             Array(String),
  f_it              Array(String),
  f_hq              Array(String),
  f_adgroup         Array(String),
  labels_json       String,
  stale_values      Array(String),
  audience_cnt_save UInt32,
  audience_cnt_now  UInt32,
  comment           String,
  saved_by          String,
  saved_at          DateTime,
  loaded_at         DateTime
) ENGINE = MergeTree ORDER BY dashboard_id;
```

## 5. Как меняется отчёт

### 5.1 Датасеты

**`ds_reports`, секция `report`** — `LEFT JOIN adoption.ta_current` и четыре
поля: `ta_status` (`none` | `active` | `stale`), `ta_version`, `ta_saved_by`,
`ta_saved_at`. Этого хватает на пометку и фильтр в каталоге.

**`ds_audience`** — новая секция `ta` (условия по отчётам области) и
изменённый отбор людей. Сейчас ЦА области = объединение «как роздан доступ»
по её отчётам. Становится: по каждому отчёту — **утверждённая ЦА, если есть,
иначе доступ**, и объединение по области:

```sql
WITH ta AS (SELECT * FROM adoption.ta_current WHERE dashboard_id IN {scope_ids})
SELECT e.user_id, ta.dashboard_id
FROM mdm_employee_daily_proteus AS e
CROSS JOIN ta
WHERE e.report_dt = {mdm_dt}
  AND (empty(ta.f_lvl3)    OR has(ta.f_lvl3,    e.lvl3_code))
  AND (empty(ta.f_lvl4)    OR has(ta.f_lvl4,    e.lvl4_code))
  AND (empty(ta.f_stream)  OR has(ta.f_stream,  e.stream_code))
  AND (empty(ta.f_spec)    OR has(ta.f_spec,    e.spec_code))
  AND (empty(ta.f_exp)     OR has(ta.f_exp,     e.exp_bucket))
  AND (empty(ta.f_it)      OR has(ta.f_it,      e.it_flg_code))
  AND (empty(ta.f_hq)      OR has(ta.f_hq,      e.hq_flg_code))
  AND (empty(ta.f_adgroup) OR hasAny(ta.f_adgroup, e.ad_groups))
UNION DISTINCT
SELECT user_id, dashboard_id FROM <доступ>            -- как сейчас
WHERE dashboard_id IN {scope_ids}
  AND dashboard_id NOT IN (SELECT dashboard_id FROM ta)
```

Те же предикаты один в один повторяет `customAudience()` в макете — значит,
макет и бой считают одинаково.

### 5.2 Вкладка «Аудитория»: откуда ЦА

Источник ЦА теперь из трёх, и он всегда назван в правом блоке шапки:

| Источник | Когда | Подпись | Действия |
|---|---|---|---|
| **Утверждённая** | у отчёта есть `ta_current` и человек ничего не менял | «Утверждена владельцем · v3 · a.petrova, 12.10.2026» + комментарий | все: «Изменить условия» (черновик), «Посмотреть по доступу» (временно) |
| **Черновик** | человек открыл конструктор и применил условия | «Черновик — не сохранён» + отличие от утверждённой | владелец: **«Сохранить как ЦА отчёта»**; все: «Вернуть утверждённую» |
| **Как роздан доступ** | ЦА нет или человек временно переключился | как сейчас | владелец: «Настроить и сохранить ЦА»; не владелец: «Настроить» (только просмотр) |

- По умолчанию при входе — утверждённая (если есть). Это и есть главное
  изменение: `S.audDef.mode` получает третье значение `saved`, и
  `audienceDef()` идёт по порядку `draft → saved → access`.
- Для **не владельца** кнопка сохранения видна, но выключена с подсказкой
  «Сохранить может владелец: a.petrova, d.sokolov». Скрывать её нельзя —
  человек не узнает, что так вообще можно и к кому идти.
  Проверка в браузере — только косметика; решает 403 из n8n.
- **Область из нескольких отчётов**: сохранение выключено («ЦА сохраняется
  на один отчёт»). Считается объединение по правилу из 5.1; в подписи —
  «у 3 из 5 отчётов утверждённая ЦА, у остальных — как роздан доступ».
- **Stale**: владельцу — плашка «2 условия больше не существуют в структуре
  (было: Департамент «…»). Пересохраните ЦА». Остальным — тихая пометка.
- **«Широкая аудитория»**: к утверждённой ЦА правило 30% не применяем (как
  к собранной сейчас) — владелец сознательно сказал, что отчёт для всех.
- Окно сохранения: условия, сколько человек и у скольких доступ (то, что
  конструктор уже считает), отличие от текущей версии, поле «зачем»,
  кнопка «Сохранить». Ответ n8n: 409 → «Пока вы редактировали, a.petrova
  сохранила v4» + кнопка «Открыть v4»; 403/422 → текст из ответа.
- После 200 ЦА сразу показывается как утверждённая (из ответа n8n), с
  пометкой «у остальных появится после синхронизации», пока датасет не
  догонит версию.

### 5.3 Вкладка «Отчёты»: пометка

- В каталоге у отчёта с утверждённой ЦА — метка «ЦА» в подписи строки
  (нейтральный `sig-chip`, не фиолетовый: фиолетовый по правилам палитры
  занят меткой «новый»), подсказка — кто и когда утвердил. Stale — та же
  метка с предупреждением.
- В фильтре «Отчёты» слева — переключатель **«с утверждённой ЦА»** рядом с
  «сертифицированные».
- Строки коллекций/владельцев: «ЦА: 7 из 12» — доля отчётов с ЦА (для
  владельца это список дел).

### 5.4 Макет (этот репозиторий)

Чтобы показать фичу до боя, в макете:

1. `data.js`: `D.savedAudience = {dashboard_id: {version, filters, saved_by,
   saved_at, comment, status}}` на ~30% отчётов, одна stale; `D.ME` —
   текущий логин и переключатель «смотреть как владелец / как гость» в
   «Как это устроено».
2. `app.js`: `audienceDef()` с тремя источниками, кнопки по таблице 5.2,
   окно сохранения, мок `saveTa()` с теми же ответами, что у n8n (200 / 403 /
   409 / 422), метка и фильтр в каталоге.
3. `_test.js`: сохранение владельцем → источник «утверждённая»; гость → 403;
   конфликт версий; stale; область из нескольких отчётов — объединение;
   число в карточке «Целевая аудитория» = числу из окна сохранения.

## 7. Открытые вопросы

1. **Как n8n узнаёт, кто вызывает.** Логин из тела запроса доверять нельзя —
   любой подставит логин владельца. Варианты по убыванию надёжности:
   (а) вызов идёт через бэкенд Proteus, который добавляет проверенный
   заголовок пользователя; (б) webhook n8n за корпоративным SSO-прокси
   (`X-Forwarded-User`); (в) n8n сам проверяет токен сессии Proteus через его
   API. В макете флоу — заглушка под (б), читает заголовок.
2. **Кто «владелец».** Список owners из метаданных Proteus (их может быть
   несколько — все равны)? Или есть отдельные «бизнес-владелец» и
   «технический»? Нужен ли белый список админов (Data Office), которые могут
   сохранять за любого?
3. **Коды в mdm.** Есть ли стабильные коды у стрима и специализации, или
   только имена? От этого зависит, насколько stale-проверка полная.
4. **Движок DLH** (Iceberg/Hive/Delta, через Trino или Spark) — чем пишет n8n
   и читает ноутбук. В файлах оставлены места под оба.
5. **Пинок синхронизации.** Есть ли у планировщика ноутбуков API запуска,
   доступный из n8n? Если нет — только расписание.
6. **CORS**: webhook должен принимать запросы с домена Proteus — если UI
   ходит в n8n напрямую, а не через бэкенд (см. п. 1).

## 8. Проверочные кейсы для флоу

| Кейс | Ожидание |
|---|---|
| владелец, первое сохранение, `expected_version: 0` | 200, `version: 1` |
| тот же запрос повторно (тот же `request_id`) | 200, та же версия, новой строки нет |
| не владелец | 403 `not_owner`, в DLH ничего |
| `expected_version` устарела | 409 + текущая версия и `saved_by` |
| неизвестный ключ в `filters` (например, `logins`) | 400 |
| пустые `filters` | 400 `no_conditions` |
| несуществующий код подразделения | 422 `unknown_values` + список |
| условия, под которые никто не попадает | 422 `empty_audience` |
| `deactivate` владельцем | 200, отчёт пропадает из `ta_current` после синка |
| DLH недоступен | 502, ответ не 200 |
| пинок синка упал | 200, `sync: "scheduled"` |
