# ClickHouse 24 в Proteus: что нельзя и как это обходить

Замерено зондами-датасетами 2026-09-18 (создание датасета = исполнение SQL, `elapsed_ms`
в ответе `proteus_dataset action=connect` — это и есть время запроса).

## 1. CTE переисполняется на КАЖДОЙ ссылке — главный источник медленных запросов
- `WITH ev AS (...)` с одной ссылкой — **2,1 с**; тот же CTE с шестью ссылками — **11,7 с** (×5,5).
  Зонды pa_ev1 / pa_ev6.
- Документация подтверждает: «ClickHouse inlines these subqueries at each point of reference,
  meaning the query is re-executed for every use case».
- Лечение из документации НЕДОСТУПНО: `AS MATERIALIZED` требует ClickHouse 25.x
  (`enable_materialized_cte`), а на кластере **версия 24** (зонд pa_chver: число строк = мажор).
  Попытка → HTTP 500 «Fatal error».
- ⇒ ПРАВИЛО: запрос датасета должен быть ЛИНЕЙНОЙ ЦЕПОЧКОЙ, каждый CTE используется один раз.
  Скалярный подзапрос (`(SELECT md FROM maxd)`) — исключение, считается однажды.
  Нужны две ветки от одного источника (каталог + ИТОГО) — размножай КЛЮЧ
  (`arrayJoin([(1, ключ), (0, '')])`), а не цепочку.

### 1.1 Плечи UNION поверх общего CTE — главный способ этот счёт взорвать
Замер 2026-09-22, прототип v7.0 (`.pa7_default.sql`): «Превышено время ожидания», ответа нет.
Причина не в объёме и не в архитектуре «куб+люди одним ответом», а в форме:
`pb` стоял в 8 плечах UNION, `pb` → `pb0`+`pbd`, каждый → `b0` → факт.
**8 × 2 + 1 = 17 сканов факта** вместо одного. Считать подстановки надо ПЕРЕМНОЖАЯ
глубину, а не складывая ссылки.

Лечение (v7.1, `.gen_cube7.py`) — размножение РОЛИ строки вместо плеч:
- `arrayJoin` выдаёт набор `(role, key, val, cut)`, в который попадает строка:
  `cat` — каталог, `list` — карточка человека, `ctx` — контекст-разрез;
- дальше ОДИН `GROUP BY role, key, val, cut`; UNION нет вообще;
- тяжёлые состояния гасятся условием ПО РОЛИ (роль — ключ группировки, поэтому
  условие обнуляет состояние целиком): `if(role='cat', kvw, [])` перед `sumMap`,
  `groupArrayIf(..., role='list' AND ...)`. Без этого один GROUP BY платит за
  массивы динамики на каждой из сотен тысяч людских групп.
- лимиты секций — `row_number() OVER (PARTITION BY role, rkey)`, а не LIMIT в плече.

Побочно выяснилось: **отдельные CTE под людей не нужны** — агрегат по человеку уже
лежит в `pa` при `kd = 0` (шина «итого»), пара человек×отчёт — при `kd = 1`.

Документация CH называет тем же лечением `GROUPING SETS`: «более эффективная
и читаемая альтернатива нескольким UNION ALL» для агрегатов из одного источника.
На платформе Proteus НЕ ПРОВЕРЕНО — размножение роли выбрано потому, что тот же
приём уже держит шину ключей в `b1` и работает в бою.

## 2. `SETTINGS` в теле виртуального датасета запрещён
`SELECT 1 SETTINGS max_threads = 4` → «Fatal error» (зонд pa_mat3). Обёртка Proteus
оборачивает SQL в подзапрос, и хвостовой SETTINGS в него не попадает.
⇒ ни одну настройку сессии из датасета не поднять.

## 3. Что ещё дорого (замеры на факте 8,1 млн строк)
- Строковая мета (имя отчёта, владелец, коллекции) через `any()` на уровне
  (ключ, логин, бакет): состояние GROUP BY хранит строки миллионы раз — **+11 с**.
  Лечение: мета отдельным узким проходом (**1,55 с**) + LEFT JOIN к готовым 6 тыс. строк.
- `groupArray` по ВСЕЙ истории вместо окна — часть той же деградации.
- Динамика (массивы бакетов) для всех 6 тыс. строк каталога — **+2,3 с**.
- Первое касание через LEFT JOIN с fd-таблицей не нужно: `max(k)` в том же GROUP BY,
  где k — возраст бакета от max_date (самый старый бакет = первый визит).
- Оконная функция `lagInFrame` для «вернувшихся» не нужна: `has(ks_win, k + 1)`.

## 3.0 Свернуть историю ДО размножения ключа (замер 2026-09-22, зонды pa7_p1..p3)
Куб держит год истории (`mk = 364`), а окну нужно `k < n2` (60 дней). Старые строки
влияют только на два скаляра — `v_life` (фильтр вселенной) и `fd_k` (первый визит),
но проходят через `arrayJoin`-размножение ключа ×4,6 и раздувают промежуток.
Лечение: в первом же GROUP BY бакет считается как `if(kexpr < n2, kexpr, -1)`,
первый визит несётся отдельным `max(kexpr) AS kmax`. Дальше `fd_k = max(kmax)`,
а ВЕЗДЕ, где раньше хватало `k < n`, обязателен нижний порог `k >= 0`
(иначе свёрнутый хвост попадёт в текущий период — тихая порча чисел).

| стадия | до | после | строк до → после |
|---|---|---|---|
| evd (+ слитый b0) | 2,23 с | 1,16 с | 6 868 576 → 2 114 860 |
| b1 (размножение ключа) | 8,00 с | 2,09 с | 31 514 931 → 8 786 669 |
| pa (массивы) | 11,39 с | 3,21 с | ks_all 31,5 → 6,27 млн |

Там же выяснилось: **отдельный CTE «разложить по бакетам» после дневной
предагрегации — пустой проход**. `pa_evd_day` уже дневная, при grain='d'
b0 отдавал ровно столько строк, сколько принимал, и стоил 0,88 с.
Бакет надо считать сразу в первом GROUP BY по сырому факту.

Грабля рядом: возраст бакета НЕЛЬЗЯ вынести алиасом (`... AS kraw`) — алиас
становится выходной колонкой вне GROUP BY, CH отклоняет. Выражение подставляется
дважды (в `if` и в `max`), генератор держит его одной константой.

## 3.1 Типы в плечах UNION ALL (грабля 2026-09-22, прототип pa7)
- `Nullable(Array(...))` в ClickHouse НЕ СУЩЕСТВУЕТ. ⇒ в плече UNION массивную колонку
  нельзя заглушить ни `NULL AS dashes`, ни `CAST(NULL AS Array(String))`
  (второе — ещё и «cannot convert NULL to non-Nullable type»).
  Только `CAST([], 'Array(String)')`. Касается всех массивов: colls, ts_*, dashes.
- `check_arms` в генераторах сверяет ТОЛЬКО ширину плеч, не типы, — такую ошибку
  ловит лишь бой. При добавлении массивной колонки проверять глазами все плечи.

## 3.3 SQL Lab отдаёт КЭШ — второй прогон того же текста не замер (2026-09-22)
`.pa6_body_default.sql`: первый прогон 16,42 с, второй — **1,57 с**. Столько запрос
исполняться не может (одна распаковка ключа даёт 31,5 млн строк), значит вернулся
сохранённый результат. При этом `.pa7_a.sql` трижды подряд дал 19,51 / 18,14 / 19,22 —
кэш срабатывает НЕ всегда, поэтому «повторил — стало быстрее» ничего не доказывает.
⇒ ПРАВИЛО ЗАМЕРА: каждый прогон — уникальным текстом. Ломать кэш строкой-комментарием
в начале (`-- cache-buster <timestamp>`): план не меняется, ключ кэша меняется.
Сравнивать между собой только ПЕРВЫЕ прогоны уникальных текстов.

## 4. Измерительные приёмы (значения датасета наружу не отдаются, только число строк)
- `proteus_describe(entity_type='dataset', dataset_id=N)` → `data_profile.rows` и `distinct`
  по колонкам. Значений НЕТ.
- Чтобы УВИДЕТЬ число: `SELECT arrayJoin(range(toUInt64(x)))` — число строк и есть x.
  `numbers(x)` для этого НЕ годится: требует константу, скалярный подзапрос роняет запрос.
- Любое утверждение проверяется запросом-нарушителем: 0 строк = держится.
- Две тяжёлые версии запроса в ОДНОМ запросе (FULL JOIN для построчной сверки) не проходят:
  «Fatal error» на 18–24 с, в том числе из-за коллизии одноимённых CTE (`maxd`, `meta`)
  в двух вложенных WITH. Сверять версии — независимыми зондами по числу строк.
