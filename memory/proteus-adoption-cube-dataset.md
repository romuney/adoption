## Люди-фильтры и мультивыбор отчётов — СЛЕДУЮЩИЙ УЗЛ
Натив-фильтров на борде нет; фильтр по людям НЕ может резать наш датасет напрямую (колонок login/lvl3 в результате нет) —
значения попадают внутрь ev через jinja: значения приходят из полки ECharts (кросс-фильтром, при проверенном допущении выше), а в SQL —
`{% set lv = filter_values('lvl3_f') %}` + `AND lvl3_management_unit_nm IN (...)` в WHERE факта.
Это локализованная джиня (один WHERE-блок на 6-8 фильтров), не зоопарк старого борда.
Мультивыбор отчётов — так же (filter_values('dashboard_f')) → точные COUNT(DISTINCT).
Корзина частоты (кросс-фильтр) — параметр freq_param тем же способом.

## Экранировка в jinja: ДЫРА НАЙДЕНА И ЗАКРЫТА (проверено зондами, не выведено)
- `where_in` (штатный фильтр Superset) в Proteus ЕСТЬ — зонд 169507.
- Но обратный слэш он НЕ экранирует: значение `x\` уронило запрос в «Fatal error»
  (в ClickHouse слэш экранирующий, литерал не закрылся). `DOMAIN\a.petrov` положил бы когорты.
- Лечение (одно место на все три подстановки):
  `{% set selq = [sel0|string|replace('\\', '\\\\')]|where_in %}` — зонд 169515 создаётся чисто.
- Числовой id — через `|int`: приведение типа само отсекает мусор.
- Практики шапки: один словарь GRAINS + `grain if grain in GRAINS else 'd'` (белый список),
  `cutn = pmode[4:]` вместо второго словаря, `pmode in [...]`, одиночность выбора как явный
  контракт (`sel|length == 1`) — мультивыбор оставляет когорты глобальными.

## Синтаксис ClickHouse, подтверждённый зондами 169510/169512
`IN` внутри лямбды работает (`arrayExists(x -> x IN ('a','b'), …)`); строковый литерал в `IN`
приводится к Int сам (`toInt32(13896) IN ('13896')` = 1); одноэлементный `('x')` — скаляр
в скобках, не кортеж (годится справа от `=` и внутрь `has()`).

## Грабли платформы (не наступать снова)
- connect ИСПОЛНЯЕТ SQL при создании (>30с — таймаут адаптера, датасет не создаётся);
  connect по СУЩЕСТВУЮЩЕМУ имени = тихий no-op (SQL не обновить). Обновление SQL — только руками в UI.
- CAST(NULL AS Nullable(Array(String))) нелегален (скаляры ок; пустые ветки → CAST([], 'Array(String)')).
- Correlated-подзапросы нельзя; колонки джойна — только через any() в GROUP BY; arrayJoin в WHERE нельзя.
- WITH-CTE переиспользуются (CSE): одинаковый текст подзапроса = одно исполнение.
- Лимит строк чарта 100К (владелец). describe(dataset) исполняет SQL и даёт rows/distinct — измерительный прибор.
- verify(mode='data') не гоняет джиня-чарты вне контекста борда (jinja-гейт невидим пробе).
- В Proteus есть чарт ECharts с JS-кастомизацией и applyCrossFilter([{column,operator,value}]).
- **ПОДМЕНА ДАТАСЕТА У ЧАРТА (proteus_set_dataset) ТРЕБУЕТ «Синхронизировать столбцы»** в UI:
  метаданные колонок остаются от старого датасета, обёртка запроса кастует по ним —
  500 CANNOT_INSERT_NULL на ровном месте (клик, 14с). Решение владельца: Sync columns
  from source — заработало. Альтернатива: убрать колонки из groupby чарта и добавить заново.
  MCP-инструмента синхронизации нет (action=refresh даёт HTTP 500 — баг сервера).
- **set_cross ПЕРСИСТЕНТЕН на драфте** (не сессионный): экспериментальную маску ОБЯЗАТЕЛЬНО
  снимать (set_cross enabled:false, filter="[]"). Незакрытая маска держит куб в sel-состоянии:
  чарту приходят только когорты, каталог пуст (выглядело как «всё сломалось»).
- .pmcp.sh — обёртка MCP (аргументы можно @file.json). Payload-файлы писать инструментом Write:
  heredoc (`<<EOF`) в этой песочнице не работает вовсе (TMPPREFIX в закрытом /tmp) — вызов уйдёт с пустым JSON.
- `proteus_dataset action=refresh` отвечает HTTP 500 (`'Datasource' object has no attribute 'response_400'`) —
  баг сервера; колонки синхронизируются при `connect`, профиль читается `proteus_describe`.
- `proteus_describe(entity_type='dataset', dataset_id=N)` — измерительный прибор: `data_profile.rows`.
  Приём: любое утверждение о данных выражается запросом-нарушителем (0 строк = держится) —
  так проверен инвариант когорт, так же можно проверять что угодно без чтения значений.
