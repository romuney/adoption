# Архитектура реализации (перезаписано по решению владельца 2026-09-16; подтверждено 2026-09-17)

Владелец решил: макет переносится в прод с почти 100% идентичностью.
НЕ натив-фильтры и не «датасет на зону» (более ранний вариант отброшен).
2026-09-17: владелец явно подтвердил — нативных фильтров на борде не будет ВООБЩЕ,
полка фильтров = кастомный ECharts-чарт. Словари 169009/169010, созданные под натив-фильтры,
вероятно, не понадобятся (решить при сборке полки).
Схема: дашборд = 2 вкладки, на каждой ПАРА кастом-чартов:
фильтры-чарт (сайдбар макета) --кросс-фильтр (setDataMask/extraFormData)--> тело-чарт (вся вкладка = 1 чарт).

Тело-чарт = порт app.js+ui.js+charts.js макета (зоны/paint, состояние внутри чарта).
Слой данных = парсер «строки куба → структуры data.js».

## Сорсы (3, виртуальные над фактом)
- S1 pa_dicts — 1 сорс под фильтры: все справочники секциями (коллекции, владельцы, АВТОРЫ,
  дерево УС 3→4, стримы, спец-ции, AD-группы + размер + is_wide, индекс отчётов с мета) → оба фильтр-чарта.
- S2 pa_reports_cube — всё тело «Отчётов»: UNION ALL секций как data.js
  (report/rts/rfreq/rmau + gkpi/gts/gfreq/gmau + глобальные ts/freq/kpi/mau/cohort по людским разрезам);
  когорты отчёта — ветка с фильтром dashboard_id (без выбора пустая). Фильтруемые колонки в зоне adhoc-WHERE.
- S3 pa_audience — по людям отдельно (зерно login: атрибуты mdm + has_access к области + came/days/views/last
  + ветки воронки и динамики охвата). ЦА-колонки с префиксом ta_* — чтобы глобальные люди-фильтры
  (lvl3 и т.п.) не задевали «Аудиторию», а ЦА не задевала «Отчёты» (кросс-фильтры матчатся по имени колонки).

## Что архитектура убивает/даёт
- Период-джиня умирает: период = UI-состояние тела-чарта, все 4 грануляции в кубе. period_column/date_filter не нужны.
- ⟳ макета = кросс-фильтр → WHERE по факту до агрегации → куб пересобирается серверно.

## Требование владельца: ВЕСЬ интерактив — на фронте, без обращения к клику (2026-09-16, «по возможности»)
Тир 1 — мгновенно и ТОЧНО на фронте (данные уже в браузере):
- период (4 грануляции в кубе), разрез каталога, сортировки, виды панелей, база раскраски когорт;
- одиночный выбор отчёта / ровно одна коллекция / один владелец (строки/г-секции в кубе);
- ИЛИ внутри ОДНОГО людского разреза — АДДИТИВНО точно (у юзера один блок/стрим/специализация,
  users по значениям одного разреза складываются без пересечений);
- вся «Аудитория» внутри области: S3 = снапшот по области (зерно login: атрибуты, has_access, came,
  active_days, views, last, first_bucket, перечень активных бакетов) → конструктор ЦА, воронка,
  пофамильно, сегменты, динамика охвата — всё клиентски.
Тир 2 — сервер (редкие действия, ⟳ как в макете): смена области «Аудитории»; И между ≥2 людскими
разрезами; пересечение людской × множественный выбор отчётов; произвольное множество отчётов
(COUNT DISTINCT); кросс-фильтр корзины частоты. Смягчение: кэш чартов Superset на повторных комбинациях.
НЕ выносится на фронт без взрыва payload: user×dashboard-зерно (~2,6 млн строк) и cut×cut-секции.

## Честные отличия от макета (согласовано)
1. Множественный выбор отчётов — серверный: в макете дедуп-формула 1/(1+.16·ln N) (симуляция),
   в проде COUNT(DISTINCT login). Одиночный отчёт/коллекция/владелец — мгновенно клиентски.
2. ⟳-действия = перезапрос (доли секунды CH + округ Superset); период/разрез/сортировки мгновенны.
3. Глобальные когорты ограничены окном факта 13 мес (или расширять окно ноды).
4. Dim отчётов — по-прежнему обязательная доработка ноды: каталог всех отчётов (0 просмотров),
   права для области «коллекция целиком», индекс отчётов для S1. В GP proteus_dashboards уже строится legacy-веткой.
5. Опции ноды: окно 24–25 мес, размеры AD-групп, first_flg, инкремент.

## Главный риск и лечение
Размер payload S2: наивно 200–250 тыс. строк (25–50 МБ). Лечение: groupArray-упаковка
(строка = отчёт × грануляция, значения массивами) → ~10 тыс. строк, единицы МБ. Замер на этапе 0.
