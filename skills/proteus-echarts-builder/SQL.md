# SQL — сборка из query-логики чарта Proteus через MCP

Читай ЭТОТ файл только когда собираешь `<name>.data.sql` из query-логики чарта
(ШАГ 2, п. 2a). SQL руками НЕ пишется: он снимается с уже настроенного графика
Proteus через MCP. Не трогаешь SQL — не читай, экономь контекст.

# 0. ОТКУДА БЕРЁТСЯ SQL: MCP PROTEUS

Источник правды — чарт eCharts Custom (`react_sanbbox`) в Proteus, где данные
заданы через «Измерения» (группировки) и «Меры» (агрегаты) в UI. Пользователь
присылает ссылку на график, из неё достаётся `slice_id`, и SQL собирается из
query-логики, которую отдаёт Proteus. Руками SQL не пишется и не выдумывается.

Порядок:

1. Достань `slice_id` из ссылки (`.../explore/?...&slice_id=783469`).
2. `proteus_chart_logic(chart_id=<slice_id>, full=true)` → query-логика чарта:
   - `groupby` — колонки группировки (это «Измерения», ключи `data`);
   - `metrics` — агрегаты (это «Меры»; пусто — значит без агрегации);
   - `filters` — условия `WHERE`;
   - `knobs.row_limit` — лимит строк;
   - `pins` — фильтры на вычисляемые колонки, `jinja` — условные ветки.
3. `proteus_describe(entity_type='dataset', dataset_id=<id>)` → контроль измерений
   и мер:
   - у каждой колонки из `groupby` в датасете `groupby: true` (размечена как
     измерение) и `filterable: true`;
   - каждая мера из `metrics` присутствует в `metrics` датасета;
   - типы колонок (`type`) — для понимания, что попадёт в `data`.
   Несоответствие → скажи пользователю: колонку нужно ВРУЧНУЮ добавить
   в «Измерения»/«Меры» в Proteus, иначе её не будет в `data`.
4. Собери `<name>.data.sql` по конвенциям §2 (алиасы, без `;`, без `FORMAT`).

Как Proteus исполняет собранный SQL и почему из `groupby/metrics` собирается
именно он — §2.

# 1. ГЛАВНОЕ ПРАВИЛО: СЧИТАЕТ JS

`data` приходит из query-логики чарта и несёт СЫРЫЕ строки нужной гранулярности.
Всё производное считается в `buildModel()`. ClickHouse — общая база, её не
нагружаем ради одного виджета.

| Считает JS (`buildModel`) | Остаётся в чарте Proteus (`groupby`/`metrics`/`filters`) |
|---|---|
| проценты, доли, разы | фильтрация по периоду и скоупу (`filters`) |
| дельты, приросты, «предыдущий период» | группировки (`groupby`) |
| ранги, топ-N, накопительные итоги | агрегаты-меры (`metrics`) |
| сортировка, поиск, пагинация | лимит строк (`knobs.row_limit`) |
| форматирование чисел и дат | |

Проверка перед тем, как просить новую колонку/меру в Proteus: «строк в браузере
от этого станет меньше?» Нет → считай в JS, не плоди меры.

**Меры и вычисляемые колонки в Proteus НЕ добавляются ради одного виджета.**
Если без новой меры график не построится — это вопрос пользователю (правило 8),
а не тихое добавление. И добавление делается ВРУЧНУЮ в Proteus, SQL потом
пересобирается через MCP.

# 2. КАК PROTEUS ИСПОЛНЯЕТ СОБРАННЫЙ SQL

Собранный запрос оборачивается в подзапрос, поверх которого Proteus строит
собственный SELECT по колонкам, выбранным в «Измерениях»/«Мерах». Отсюда жёсткие
следствия для сборки:

- **Никакой `;` в конце и никакого `FORMAT`** — подзапрос сломается.
- **`ORDER BY` внутри НЕ гарантирован**: внешний запрос и серверная пагинация его
  перебивают. Порядок задавай явным `sort` в `buildModel()` (RETRO 18).
- **Лимит строк применяется СНАРУЖИ** и молча обрезает выборку. Нужен честный
  итог — отдельной мерой в Proteus (`metrics`), не гоняй лимит.
- **Не-аддитивные величины опасны**: если Proteus сагрегирует готовый процент,
  получится среднее от процентов. Доли в `metrics` не выноси — отдавай числитель
  и знаменатель отдельными колонками, дели в JS.

## Именование колонок

Колонки приходят из `groupby`/`metrics` чарта. Если имя не подходит под
`snake_case` латиницей (пробелы, скобки, кириллица, агрегат вроде
`sum(amount)`) — задай явный алиас, иначе в JS не взять точечной нотацией.

```sql
-- НЕТ: имя станет 'sum(amount)', в JS не взять точкой
select toStartOfMonth(dt), sum(amount) from t group by 1
-- ДА
select toStartOfMonth(dt) as period, sum(amount) as revenue from t group by period
```

Собранный по `groupby`-колонкам из примера (слайс 783469, датасет hier_unit_dict):

```sql
select
    lvl,
    rk,
    nm,
    parent_rk,
    head_full_nm,
    head_ad_login
from hier_unit_dict
limit 10000
```

# 3. ЧЕГО В CLICKHOUSE 24.8 НЕТ

| Стандартный SQL | В 24.8 писать так |
|---|---|
| `lag(x, 1) OVER (...)` | `lagInFrame(x, 1) OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)` |
| `lead(x, 1) OVER (...)` | `leadInFrame(x, 1) OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)` |
| `GROUPS BETWEEN ...` | только `ROWS` или `RANGE`; «по группам» — через `dense_rank()` в подзапросе |
| `RANGE BETWEEN INTERVAL '7' DAY PRECEDING ...` | `ORDER BY toUnixTimestamp(ts) RANGE BETWEEN 604800 PRECEDING AND CURRENT ROW` |
| `ORDER BY d WITH FILL ... STALENESS ...` | модификатора нет — ограничить `FROM`/`TO`, хвост обрезать в JS |
| `toStartOfInterval(t, INTERVAL 1 WEEK, origin)` | 3-й аргумент в 24.8 — ТАЙМЗОНА, не origin |
| `generate_series(date, date, interval)` | `select toDate('...') + number from numbers(N)` |
| `QUALIFY` без оконной функции | `WHERE` |
| `first_value(x)` со стандартным RESPECT NULLS | `first_value(x) RESPECT NULLS OVER (...)` — иначе NULL пропускаются |
| `ON a.x = b.y` с NULL в ключе | `ON isNotDistinctFrom(a.x, b.y)` — иначе строки исчезают |
| `x / 0` → ошибка | вернёт `inf`/`nan`, см. §4 |

`lagInFrame`/`leadInFrame` без ЯВНОЙ рамки почти всегда врут: рамка по умолчанию —
`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, будущих строк в ней нет,
поэтому `leadInFrame` вернёт дефолт. Есть `ORDER BY` в окне — пиши рамку явно.

Лучший вариант для этого проекта: **сдвиг на предыдущий период не считать в SQL
вообще** — отсортировать `data` в `buildModel()` и взять соседний элемент массива.

Доступно и работает: `row_number`, `rank`, `dense_rank`, `nth_value`,
`sum/avg/count/min/max OVER`, именованные окна `WINDOW w AS (...)`, `QUALIFY`
(с оконной функцией), обычные `WITH ... AS (...)`, `ASOF JOIN`, `FULL OUTER JOIN`.

# 4. ЛОВУШКИ, КОТОРЫЕ МОЛЧА ПОРТЯТ ЦИФРЫ

**Деление.** `x / 0` не падает, а даёт `inf`/`nan`, и в JSON это приезжает как `null` —
метрика молча исчезает. `intDiv(x, 0)` наоборот роняет ВЕСЬ запрос (код 153), и виджет
остаётся пустым. Правило: доли считать в JS; если делить в SQL — только
`if(d = 0, 0, x / d)`, целочисленно — `intDivOrZero(x, d)`.

**LEFT JOIN.** `join_use_nulls = 0` по умолчанию: непопавшие строки заполняются
дефолтом типа (`0`, `''`), а не NULL. «Нет данных» и «настоящий ноль» становятся
неотличимы. Либо добавь в правую часть маркер `1 as has_row`, либо оборачивай метрики
в `ifNull(x, 0)` осознанно. NULL в ключе JOIN не совпадает ни с чем, включая другой
NULL, — строки просто выпадают, и итог не сходится с общей суммой.

**Недели.** `toStartOfWeek(dt)` без режима режет по ВОСКРЕСЕНЬЮ, а `toMonday(dt)`,
`date_trunc('week', dt)` и `toStartOfInterval(dt, INTERVAL 1 WEEK)` — по понедельнику.
Смешал в одном отчёте — факт и план разъехались на сутки. Используй `toMonday()`.

**Типы дат.** `toStartOfMonth/Quarter/Year`, `toMonday` → `Date`;
`toStartOfDay/Hour/Minute` → `DateTime`; `date_trunc` — по-разному в зависимости от
единицы. Приведи ключ периода к ОДНОМУ типу по всей витрине. В `data` дата приезжает
epoch-числом, а не строкой из UI-таблицы (RETRO 10): либо гони через `toDate()` в JS,
либо отдавай готовую строку `formatDateTime(d, '%Y-%m-%d')`. В `formatDateTime`
минуты — это `%i`; `%M` означает имя месяца.

**Точность.** `uniq()` и `quantile()` приближённые, `quantile` вдобавок
недетерминирован. Там, где пользователь сверяет цифру руками, — только `uniqExact()`
и `quantileExact()`.

**Недетерминированность.** `any()`/`anyLast()` возвращают произвольное значение группы.
«Значение на последнюю дату» — это `argMax(field, dt)`, а не `anyLast(field)`.
При ничьей в `argMax` добавь тай-брейк.

**Прочее.** Арифметика на `UInt` переполняется: `a - b` при `b > a` даёт огромное
положительное число — приводи к знаковому типу перед вычитанием. Комбинатор `-If`
(`sumIf`, `countIf`) при нулевом числе совпадений возвращает `0`, а не NULL. `count(col)`
и `count()` считают разное. `groupArray` молча теряет NULL — если важны позиции,
пиши `groupArray(ifNull(x, 0))`. `LIMIT n BY` без явного `ORDER BY` даёт произвольные
строки. CTE в ClickHouse НЕ материализуется: `WITH t AS (SELECT ...)` подставляется как
код и выполняется заново при каждом упоминании. Скалярная форма пишется наоборот —
`WITH (SELECT ...) AS x`.
