# Proteus Adoption NEXT — установить рядом с текущим отчётом

Это отдельная экспериментальная поставка: новый ноутбук Helicopter, новые физические таблицы `pa_next_*`, три новых датасета и три новых чарта. Один чарт показывает весь интерфейс; два служебных чарта параллельно получают каталог и показатели. Текущий отчёт продолжает использовать прежние объекты.

Источник отбора просмотров — **переданный тобой `Proteus Adoption (4).yaml`**, а не старый `Helicopter.yaml`. Сохранены обе ветки событий, граница 06.10.2026, верхняя граница текущей полуночи и кратность соединений. Подробности: [DATA.md](DATA.md), [договор сходимости](Проверки/Методология.md).

Поставка готовится для контролируемого теста на отдельном борде. Локальные проверки и их пределы приведены в [результатах](Проверки/Результаты.md). Корпоративные права, `gp_to_click`, кэш и фактическую загрузку iframe проверяешь при установке. При ошибке или расхождении — **остановись на этом шаге**, не переноси объекты в старый отчёт.

## Обновить установленную экспериментальную ноду

Текущий YAML создаёт **все GP-таблицы в рабочей схеме Helicopter**, без префикса `usr_cross_data.`. Обновлены все ссылки и выгрузка; у каждого параграфа русское название по действию. Для перехода с прежней версии переимпортируй **файл 1 целиком в экспериментальную ноду `pa_next`**. Если менял настройки ноды вручную, сохрани их перед импортом. Закрой новый борд, выполни ноду сверху вниз, затем файл 11 и принудительное обновление чартов. SQL датасетов и JS чартов менять не требуется.

Исправление `chr(894)` также включено. Файл 12 — отдельная копия параграфа «Подготовить атрибуты людей, права и словари (ускорение 1a)» текущей версии; одной его замены недостаточно для перехода со старой схемы. Подробности: [рабочая схема](<Проверки/Рабочая схема.md>), [исправление кодировки](<Проверки/Исправление кодировки.md>).

## 1. Создать и проверить новый ноутбук

1. Проверь, что префикс `pa_next_` в рабочей схеме GP и базе ClickHouse `prod_proteus` ещё не занят другим проектом. Новые имена перечислены в DATA.md. Повторный запуск заменяет именно эти экспериментальные таблицы.
2. Импортируй файл 1 в экспериментальную ноду. GP-параграфы и Python-выгрузка должны использовать одну рабочую/временную схему Helicopter. Нужны права чтения общих источников и создания таблиц в рабочей схеме; права записи в `usr_cross_data` не требуются. Секреты в YAML не встроены.
3. Проверь, что доступны корпоративные модули `tactuality` и `proteus_py.database.clickhouse`. Они уже использовались в исходной ноде. Новая нода не требует предварительного выполнения старой.
4. На время загрузки закрой новый борд и не используй его: последовательная выгрузка не даёт атомарного снимка сразу всех таблиц. Запусти новый ноут целиком сверху вниз. Не запускай вторую копию одновременно и не запускай отдельно последний параграф. Дождись успешного завершения всех параграфов и сообщения `PA NEXT: all data tables uploaded; generation published ready`.
5. Выполни файл 11 в SQL Lab. Ожидается **21 строка**, во всех `ready = 1`, `publication_state = ready`, одинаковый `published_run`. Пустые бизнес-таблицы возможны. Ошибка отсутствующей таблицы, разные версии либо `ready = 0` — дальше не идти.

Дополнительно выполни в GP [проверку неоднозначных последних атрибутов](<Проверки/GP — неоднозначные атрибуты.sql>). В исходной методологии при разных атрибутах в один последний день выбор строки не полностью определён. Ожидаются нули; ненулевой результат — повод разобрать конфликт до приёмки цифр, а не добавлять новый порядок выбора наугад. Это диагностический GP-запрос, не SQL Lab ClickHouse.

В новой ноде нет старых REST-логов, фильтров/справочников для прежних отчётов, старых экспортов и прогрева старого борда. В неё включены только зависимости новых физических витрин. При сбое выгрузки дальнейшие вызовы прекращаются; исправь причину и перезапусти **весь** ноутбук. Если сбой произошёл до записи `loading`, может сохраниться прежний manifest; он не подтверждает успех нового запуска. Это последовательная публикация с проверками версии, не атомарная транзакция сразу всех таблиц.

## 2. Создать три новых датасета и чарта

1. Создай виртуальные датасеты по таблице выше. Вставь соответствующий SQL целиком, сохрани, синхронизируй колонки.
2. В каждом датасете должно быть ровно пять результирующих колонок: `section`, `g`, `k`, `parent`, `n`. Служебные секции версии и запроса не отфильтровывать.
3. Создай три новых чарта типа eCharts / `react_sanbbox` на этих датасетах. В «Измерения» добавь **все пять колонок**, включая `n`. Метрики, дополнительную сортировку, временной фильтр и фильтр по `section` не добавляй. Лимит строк — **50 000**. Носители кросс-фильтров не добавляй в измерения.
Для первичного сохранения нового чарта до привязки ID можно временно использовать `option = {series: []};`. После привязки обязательно замени его полным JS своей роли.

4. Для первоначального теста явно установи **положительный Cache timeout = 60 секунд** у всех трёх новых датасетов и новых чартов (поле времени кэширования в настройках). Значения 0/пусто могут наследовать долгий кэш. Это настройка только нового отчёта. На текущем форке проверь, что лимит действительно применяется: позднее сверяй версию ответа с файлом 11.
5. Запиши ID созданных чартов. Сначала главный, затем загрузчик каталога, затем загрузчик панели. В поставке стоят намеренные заглушки 910001/910002/910003: до их замены обмен работать не будет.

## 3. Привязать ID и собрать борд

В облачном checkout ветки `new` выполни, подставив **свои новые ID** и уникальное имя канала:

```bash
python3 tools/parallel/build_ui.py --main 123001 --cat 123002 --one 123003 --channel adoption-next-board-123
python3 tools/parallel/build_ui.py --check
```

Это пересоберёт JS 4/6/8, CSS 9 и JSON 10 согласованно. Зависимости для повторной сборки и альтернативный путь Node-пакетов указаны в [UI.md](UI.md). Если работаешь через облачный чат, передай три новых ID — их можно привязать этой же командой. Не делай массовую замену чисел в минифицированном JS вручную.

1. Вставь свежие файлы 4/6/8 в три соответствующих чарта и сохрани.
2. Создай отдельный дашборд. Оба загрузчика поставь в первый отдельный ряд **над главным чартом**; в этом ряду не должно быть других чартов. Главный чарт — следующим рядом во всю ширину, начальная высота ячейки 900–1100 px. Все три — на одной активной вкладке. Первый ряд нужен, чтобы скрытые CSS загрузчики с положительной высотой 2 px попадали в видимую область при открытии: платформа может откладывать монтаж чартов ниже экрана.
3. Вставь CSS из файла 9. Он скрывает служебный ряд, сохраняя загрузчикам ненулевые размеры и возможность запуска. В режиме редактирования загрузчики видны. Не заменяй это на `display:none` и не переносись на неактивную вкладку.
4. В JSON-метаданных добавь поля файла 10, сохрани остальные поля дашборда. Это **фрагмент**, не весь JSON-экспорт. Кросс-фильтры включены, самовлияние выключено: главный → оба загрузчика; каталог → панель; панель → каталог. На главный чарт загрузчики не влияют.
5. Сохрани и обнови весь дашборд с принудительным обновлением запросов. После каждого нового запуска ноды обновляй весь борд и сверяй версию данных с файлом 11.

Обычная перезагрузка страницы или Ctrl/Cmd+Shift+R очищает браузерный кэш, но не гарантирует обновление данных на сервере. Нужен режим принудительного обновления **всех трёх чартов** в Proteus; в запросе `chart/data` проверь `force=true` и совпадение `pa_next_version.k` с `published_run`. Если такого режима нет, дождись истечения заданных 60 секунд и обнови все запросы, затем всё равно проверь run_id. Если версия не обновляется, останови приёмку и проверь применение cache timeout на текущем форке.

Значения `cache_timeout=0/-1` в исторических документах противоречат друг другу. Не меняй на их основании настройки старого борда. Для теста используй принудительное обновление и убедись по ответам запросов, что пришёл текущий `pa_next_version.k` из `published_run`, а не только согласованный старый кэш.

## 4. Сверить рядом с действующим отчётом

Сравнивай под одним пользователем, при одинаковой свежести источников, одинаковом периоде и одинаковых фильтрах. Новый ноут читает текущие источники; сравнение с данными старого борда за вчера не доказывает расхождение формулы.

- Без выбора: KPI, итог каталога, динамика, MAU, ЦА и закрепляемость для четырёх готовых периодов.
- Один отчёт; несколько отчётов с общими зрителями; коллекция; владелец. Итого уникальных людей должно сохранять дедупликацию.
- «Мои», «Без владельцев», опубликованные/актуальные; ЦА по правам и по условиям; старый и новый логин одного человека.
- Свой период, границы месяца/квартала, длинное окно, пустая выборка и окно вокруг 06.10.2026.
- Выбор каталога меняет только панель; выбор людей панели меняет только каталог. Быстрые последовательные выборы не должны подменяться поздним старым ответом.
- Второй пользователь с другими правами/логином; повторное открытие и обновление после нового запуска ноды.

Отдельно сними Network-время первого открытия, повторного открытия, выбора отчёта, смены периода и фильтра по людям. Записывай дату данных и состояние кэша. Уменьшен JS в интерактивных запросах и добавлен предрасчёт GP для типовых состояний; конкретное ускорение каждого сценария определяется замером, а не обещается.

## Если что-то не так

| Симптом | Действие |
|---|---|
| Красный GP/Python-параграф | Не идти дальше; сохранить номер параграфа и полный текст ошибки без секретов; исправить причину, перезапустить всю новую ноду |
| `no schema has been selected to create in` | Выбрать рабочую схему Helicopter вместо `usr_cross_data`; GP и Python-выгрузка должны разрешать таблицы в одной рабочей схеме |
| Файл 11 даёт ready=0 или ошибку | Проверить полный успешный экспорт; не публиковать ready отдельно |
| Блок не загрузился | Проверить, что оба загрузчика смонтированы на активной вкладке, ID совпадают во всех пяти файлах, области фильтров сохранены |
| «Части отчёта относятся к разным загрузкам» | Дождаться завершения ноды, принудительно обновить запросы всех трёх чартов на сервере; сверить run_id с SQL Lab |
| Главный iframe пересоздан, выбор не восстанавливается | Сбросить фильтры дашборда и обновить страницу целиком, как просит сообщение; старые значения не угадываются |
| Числа отличаются | Не переносить в текущий отчёт. Зафиксировать период, фильтры, свежесть, название показателя и обе цифры; разбирать источник расхождения |
| Лишнее пустое место под отчётом | Загрузчики должны быть вместе в отдельном ряду. Проверить применённые ID в CSS и реальные классы текущего форка |

Откат эксперимента — остановить расписание новой ноды и закрыть новый борд; старые объекты не менялись. Автоматического DROP для очистки нет. После принятия чисел и UX замена в действующем отчёте — отдельный шаг с сохранением прежнего JSON/CSS: новый протокол использует **три связанных чарта**, поэтому перенос одного JS без загрузчиков и направлений фильтров недостаточен.
