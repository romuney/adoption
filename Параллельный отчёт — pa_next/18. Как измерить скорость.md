замени содержимое существующего Markdown-контрола текстом файла14 с `#app`.
Это обновление оформления, JS/SQL для него не меняются. Подробности — в
[актуальном начале инструкции](<0. Начни здесь.md>).

Ускорение на проде пока не измерено. Текущая правка добавляет начальный CROSS DATA,
убирает повторную пересылку готовых ответов и делает доступным замер этапов.
Сами SQL и расчёты не меняются. Ощущение «примерно в4раза медленнее» — важный
сигнал владельца; локальная проверка не устанавливает его причину.

## Установить подготовленную правку

В отдельном борде `pa_next` заменить целиком:

| Чарт / настройка | Файл |
|---|---|
| Основной859562 | [4. JS](<4. JS — весь отчёт.js>) |
| Каталог859563 | [6. JS](<6. JS — загрузчик каталога.js>) |
| Панель859564 | [8. JS](<8. JS — загрузчик панели.js>) |
| Общий CSS борда | [9. CSS](<9. CSS — дашборд.css>) |

Сохранить и обновить страницу борда. SQL, ноду, Markdown и JSON для этой правки
обновлять не требуется. На первоначальном ожидании появляется крупный знак220px
и спокойная линия; это фон под iframe, не перекрывающий управление. Внутри
загруженного отчёта остаются прежние небольшие индикаторы ожидания данных.

## Быстрый замер без доступа к корпоративной базе из облака

1. Открой новый борд и дождись первой загрузки. В DevTools → Console выбери
   контекст **top**. Вставь **весь файл16** ([скрипт](<16. Консоль — скорость загрузки.js>)).
   Это консоль браузера, не редактор JS чарта и не SQL Lab.
2. Выполни `copy(await __paNextPerf.finish())`. Сохрани буфер как
   `new-first-load.json`. Здесь будут уже имеющиеся ResourceTiming с начала
   навигации и автоматически записанные этапы первого запуска нового отчёта.
3. Снова вставь файл16. **Не перезагружай страницу**: перезагрузка удалит
   перехватчики. Через штатное меню борда принудительно обнови данные всех
   чартов, дождись завершения; повтори три раза с тем же периодом и условиями.
   Затем выбери отчёт, другой отчёт, сбрось выбор и смени период. Экспортируй
   тем же `copy(await __paNextPerf.finish())` в `new-refresh-and-clicks.json`.
4. Открой старый рабочий борд с теми же периодом, условиями ЦА и выбором отчётов.
   Повтори пункты1–3, сохрани `old-first-load.json` и `old-refresh-and-clicks.json`.
   В старом борде `report:[]` нормально: внутреннего нового измерителя там нет;
   сетевые времена доступны независимо от него. `chartSlots` настроен на новые
   ID859562/859563/859564: на старом борде он может быть пустым, это нормально. Не меняй старые SQL/JS.
5. В Proteus SQL Lab на том же подключении ClickHouse запусти **одним запросом**
   [файл17](<17. SQL Lab — настройки для замера.sql>) и сохрани его одну строку
   как `clickhouse-settings.json`. Запрос ничего не создаёт и не меняет.
6. Добавь эти файлы в репозиторий, например в `Проверки/Замер скорости/`, и сообщи,
   что они загружены. Также укажи браузер и примерное время первого открытия
   старого/нового борда; достаточно в тексте. Не меняй настройки кэша ради замера.

Браузерные Network timings не всегда выделяют чистое выполнение SQL. Если
потребуется именно переписать медленный запрос, следующий точный вход —
отрендеренный SQL проблемного чарта из штатного просмотра запроса и время его
исполнения в SQL Lab, три попеременных прогона старой/новой версии. Если пункт
просмотра запроса недоступен, сначала достаточно файлов выше: они покажут,
на каком участке нужен следующий замер.

## Что покажет запись

| Данные | Что проверяем |
|---|---|
| `resources` | Начало запроса, первый байт, конец ответа, размеры передачи/декодирования; исторические записи до запуска консоли тоже включены |
| `requests` | Чарт из `slice_id`, HTTP-статус, начало и получение заголовков fetch либо окончание XHR; опрос асинхронных задач виден отдельно |
| `chartSlots` | Были ли оба загрузчика смонтированы и в видимой области, был ли native loading/error |
| `longTasks` | Долгие задачи главного потока браузера; отсутствие поддержки не означает отсутствие задержек |
| `report[].performance` | Запуск JS, длительность вызова рендерера, принятие ответа, первая готовность обоих наборов данных, последующие запросы |

`epoch + event.at` совмещает часы iframe с часами top. `render.duration` — время
вызова рендерера, не чистая загрузка SQL и не замер фактического paint.
`rows-accepted.duration` включает путь с регистрации запроса до ответа;
первоначальная регистрация начинается после запуска JS шапки. Поэтому суммарное
время первого входа определяется вместе с навигацией/ресурсами в top.
`initial-ready` — состояние готовности принятых данных и вызовов рендереров;
время загрузки страницы до появления iframe находится в top, а не внутри него.

У fetch `headersAt` наступает до полного чтения тела. Для полного ответа нужно
смотреть `resources.responseEnd`, а не принимать `headersAt` за окончание.
Размер0 может означать недоступную браузерную статистику. ResourceTiming имеет
ограниченный буфер; отсутствие старой записи не доказывает отсутствие запроса.
Кэш результата Proteus и HTTP-кэш браузера — разные уровни. Флаг `is_cached`,
если его показывает Network/штатный интерфейс, полезно отдельно отметить.

Скрипт не читает тела ответов и не запускает запросы к данным. Значения фильтров,
SQL, URL, токены, cookies и storage в экспорт не попадают; распознаётся только
номер чарта в уже существующем запросе. Перехватчики снимаются после finish,
stop или5минут. Результат — одна пользовательская сессия, не RUM и не статистика
всех пользователей.

## Как выбирается следующая оптимизация

- Если задержка до ответа SQL — отдельно разбираем планирование Superset/Jinja,
  очередь асинхронных задач и выполнение ClickHouse. Настройки, индексы и
  запросы меняются после замера и точной сверки всех чисел.
- Если ответ каталога большой и долго считается — проверяем стоимость блока
  preview, который подготавливает будущие клики. Возможный вариант — получать
  тяжёлые предрасчёты после первого рабочего экрана. Сейчас это гипотеза,
  не внедрённое изменение методологии или архитектуры.
- Если ответы готовы, а интерфейс запаздывает — смотрим передачу между iframe,
  размер данных, парсинг и рендер. Устранение повторных ROWS уже включено.
- Если служебные чарты стартуют поздно — проверяем реальный lazy mount и порядок
  строк борда. Старая диагностика14.11 показывала их ниже экрана; текущий CSS на
  локальном стенде держит их внутри видимой области. Это не доказательство
  поведения корпоративного форка.

Правила источников: Performance → измерить одинаковые сценарии до/после;
Proteus CH-02/CH-31 → ClickHouse24.8 с новым анализатором, попеременные замеры
и точная сходимость ответа; ClickHouse `query-join-filter-before` → сокращать
читаемые наборы до JOIN только после подтверждения узкого места. Источники
закреплены в [базе знаний](../docs/knowledge/README.md).
