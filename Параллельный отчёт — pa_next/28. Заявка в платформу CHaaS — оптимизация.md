# Proteus Adoption NEXT на кластере proteus-cross — что просим у платформы

Отчёт Proteus Adoption NEXT (дашборд на базе «Proteus CROSS CHaaS») после переезда на кластер стал заметно
медленнее старой базы. Свой SQL мы уже переделали под кластер. Остаток упирается в раскладку таблиц.

## Факты (замеры 25.11, SQL Lab)

- Кластер: ClickHouse 25.8.12, 6 шардов × 2 реплики, узел 4 CPU / 12 GB, `distributed_product_mode = global`.
- Наши таблицы — `prod_proteus.pa_next_*`, 23 штуки. Пишутся выгрузкой `gp_to_click` из GP раз в сутки.
  Маленькие: самая большая `pa_next_evd_day` — около 9,4 млн строк; `pa_next_pair` — 1,1 млн;
  справочники — от сотен до 82 тыс. строк. При этом **каждая разложена на все 6 шардов** (`_shard_num` почти поровну).
- Один и тот же запрос панели:

| Где | Время |
|---|---|
| старая база (24.8, один сервер) | 2,9 с |
| кластер, SQL до переделки | 16,8 с |
| кластер, SQL после переделки (уже в бою) | 5–6 с |
| кластер, без нашей проверки версии данных (только замер) | 3,8 с |

Сами данные считаются за миллисекунды на шард. Время уходит на координацию: в одном запросе десятки
подзапросов, и каждый — поход на 6 шардов со сбором результата на одном узле.

## Что просим (шардирование остаётся — 26.11 платформа подтвердила, что без него нельзя)

### 1. Ключ шардирования для таблиц факта — главное

Сейчас строки разложены по шардам случайно (`_shard_num` почти поровну). Просим шардировать по `dashboard_id`:
`pa_next_evd_day`, `pa_next_pair`, `pa_next_pair_acc`, `pa_next_dash_day`, `pa_next_dash_bkt`.

Зачем. Самые тяжёлые запросы отчёта («Свои даты», 15–20 с) агрегируют факт по паре «отчёт × сотрудник» и
соединяют его с парами. При случайной раскладке каждый узел шлёт частичные итоги на один узел, и соединение
идёт через рассылку временной таблицы на все узлы. По журналу запросов 26.11: в одном запросе каталога 4 чтения
факта, до 6 с на шард, 3,4–3,6 ГБ памяти на инициаторе. С ключом `dashboard_id` всё, что относится к одному
отчёту, лежит на одном шарде, и эти расчёты досчитываются на месте. Объём хранения не меняется.

Вопрос: можно ли задать ключ при выгрузке `gp_to_click`, например параметром `sharding_key` или выражением
движка Distributed?

### 2. Чтение со второй реплики

`enable_parallel_replicas = 1`, `max_parallel_replicas = 2` (+ `cluster_for_parallel_replicas`) — для пользователя
Proteus или хотя бы для `prod_proteus.pa_next_*`. Сейчас из двух реплик шарда читает одна; тяжёлые чтения факта
идут до 6 с на шард. В 25.8 это бета — нужна ваша оценка; предлагаем начать с тестового пользователя.

### 3. Не менять

`use_query_condition_cache = 1` (на нём держится наша проверка версии данных), `distributed_product_mode = global`,
`max_threads = 4` (у узла 4 ядра).

### 4. Журнал запросов — уже есть

Через `clusterAllReplicas('{cluster}', \`system\`.query_log)` журнал читается из SQL Lab. Его достаточно, отдельный доступ не нужен.

## Как проверим результат

В SQL Lab на базе CHaaS — файлы поставки «22. SQL Lab — проверка панели одним запросом.sql» и
«20. … каталога …». Сейчас: панель 5–6 с, каталог около 4 с. Цель после п. 1 — панель около 3 с.
