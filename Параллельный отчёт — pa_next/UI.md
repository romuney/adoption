# Чарты экспериментального отчёта

Это **отдельный новый дашборд**, три новых чарта и три новых виртуальных датасета. Старые датасеты/чарты не заменять. Физические таблицы — только `pa_next_*`; источник и установка ноды описаны в основной инструкции поставки.

| Новый чарт | SQL датасета | JS | Что делает |
|---|---|---|---|
| Весь отчёт, `pa_next_head` | `3. SQL — шапка.sql` | `4. JS — весь отчёт.js` | Единственный видимый интерфейс: настройки, каталог и панель |
| Загрузчик каталога, `pa_next_cat` | `5. SQL — каталог.sql` | `6. JS — загрузчик каталога.js` | Получает каталог, передаёт строки главному чарту; эмитит выбор каталога |
| Загрузчик панели, `pa_next_one` | `7. SQL — панель.sql` | `8. JS — загрузчик панели.js` | Получает показатели, передаёт строки главному; эмитит фильтры людей |

Во всех трёх чартах: тип Proteus eCharts/`react_sanbbox`; «Измерения» **все пять**: `section`, `g`, `k`, `parent`, `n`; без метрик, сортировки, дополнительного временного фильтра и выборочной фильтрации секций. Лимит 50 000 строк. Дополнительные параметры шаблона не нужны; роль загрузчика задаёт его JS. Служебные строки `pa_next_version` и `pa_next_request` обязательно должны доехать до JS. Носители фильтров не добавлять в «Измерения».

## Привязка новых ID

Поставка привязана к ID, переданным владельцем: **859562** — основной чарт, **859563** — загрузчик каталога, **859564** — загрузчик панели. Готовые JS/CSS/JSON уже содержат эти значения и канал `proteus-adoption-next-859562`. Для повторения сборки из корня checkout:

```bash

python3 tools/parallel/build_ui.py --check
```

Для другого комплекта чартов подставь его ID и уникальный channel. Сборщик согласованно обновляет JS 4/6/8, CSS 9 и JSON 10; после этого вставляй их целиком. При следующей сборке без аргументов используются сохранённые ID из `src/ui-build.json`. Не меняй ID вручную в минифицированном коде. Channel должен быть уникальным для данного экспериментального борда, особенно если на одной странице размещают несколько отчётов.

Сборка требует Python 3.9+, Node.js **20.19+ в ветке 20, 22.13+ в ветке 22 либо 24+** (требование ESLint; проверено на Node 24.22.1) и **terser 5.51.2 + ESLint 10.1.0**. В облаке пакеты установлены вне репозитория в `/workspace/.deps/node/node_modules`. В другом checkout: `npm install --prefix /tmp/pa-next-node --no-save terser@5.51.2 eslint@10.1.0`, затем `export PA_NEXT_NODE_PATH=/tmp/pa-next-node/node_modules` перед обеими командами сборки выше. TLS и проверки пакетов не отключать. Код сжимает закреплённый `docs/vendor/proteus-playbook/kit/min.cjs`; он проверяет ES5, глобальный `option` и отсутствие выполнения кода из строк. До записи проверяются исходный объединённый JS и сжатый результат через ESLint, включая `no-undef`.

## Размещение и области фильтров

На одной активной вкладке поставь оба загрузчика отдельными ячейками в **первый ряд над главным чартом**. В этом ряду должны быть только загрузчики. Главный чарт размести следующим рядом на всю ширину. В просмотре его высота автоматически следует окну; ручная высота нужна только для раскладки в редакторе. Вставь `9. CSS — дашборд.css` в CSS **нового** борда. Загрузчики сохраняют положительные размеры 2 px; `display:none` не используется. Первый ряд должен попадать в видимую область при открытии: платформа может откладывать монтаж чартов ниже экрана. В режиме редактирования скрывающие правила не действуют. Не клади загрузчики на неактивную вкладку: платформа может не запускать её чарты. Фактический монтаж обоих загрузчиков нужно подтвердить на новом корпоративном борде.

В JSON-метаданных **нового** дашборда внеси поля из `10. JSON — области фильтров.json`, сохранив прочие поля дашборда. Это фрагмент метаданных, не полный экспорт дашборда. `show_native_filters: false` и пустая `native_filter_configuration` отключают native filters. Верхняя шапка борда, название и кнопка редактирования остаются видимыми. CSS скрывает только шапки новых чартов и их меню в просмотре, возвращая их в редакторе. Высота учитывает меню Proteus (48 px), шапку борда (65 px) и поля. При отсутствии меню или шапки их резерв снимается. Включены кросс-фильтры; самовлияние выключено:

- Главный чарт → загрузчик каталога и загрузчик панели.
- Загрузчик каталога → только загрузчик панели.
- Загрузчик панели → только загрузчик каталога.

Главный JS не шлёт все фильтры от одного источника. Он передаёт команду соответствующему загрузчику, а тот вызывает свой `applyCrossFilter`. Команды подтверждаются и дедуплицируются; потерянное уведомление восполняется запросом данных. Колонки и формулы исходных рендереров сохранены; обновлён только монтаж, транспорт и оболочка. Фильтры по людям не меняют их собственную панель; выбор каталога не меняет исходный каталог.

## Очередь и возврат готовых результатов

Единая оболочка хранит последний выбор отдельно от реально отправленных фильтров. Для каждого получателя одновременно выполняется один запрос; изменение общих настроек ждёт освобождения обоих. Завершение определяется точными nonce того запроса, даже если пользователь уже выбрал другое. ACK подтверждает доставку команды, но не завершение SQL. Промежуточные клики объединяются; старый ответ может пополнить кэш, но не заменяет текущие числа. Задержка SQL сама по себе не запускает повторный запрос. Ошибка отправки команды показывает локальную кнопку повтора.

Полные ответы кэшируются только в памяти текущего iframe и пользовательской сессии, отдельно по поколению витрин и набору бизнес-фильтров. Ключ сохраняет точные строки и порядок массивов, включая пустые атрибуты; nonce в бизнес-ключ не входит. Нормализованы только доказанные SQL-дефолты. Сброс и возврат к сохранённому выбору немедленно восстанавливают все вкладки. При новом поколении кэш очищается. В каждой части хранятся до 16 ответов; при давлении на память старые вытесняются (ориентир 24 MiB, единственный большой ответ сохраняется). Сброс в давно вытесненное состояние снова требует полного ответа.

Готовность не рисуется отдельной полосой. При недоступных числах вкладки остаются активны, старые KPI и область заголовка скрыты, один индикатор находится в теле вкладки и появляется с задержкой 400 мс. При preview исходный рендерер сохраняет готовые KPI/динамику/календарь и показывает локальное ожидание только отсутствующих деталей.

На ноутбуке внутри единого чарта можно прокрутить верхние фильтры вверх. Аналитика сохраняет полезную высоту вместо сжатия обоих графиков. На высоком экране фильтры и аналитика помещаются вместе; шапка самого борда с редактированием остаётся видна. Календарь измеряет ширину правой панели, а не всего общего iframe.

## Проверка версии и фильтров ответа

Ответ принимается только с `pa_next_version: n=1, parent=ready` и тем же `k` (run_id), что у главного чарта. Проверяются полное эхо фильтров, отдельный точный nonce запроса, роль, channel, отправитель, экземпляр загрузчика и порядковый номер. Нормализация исторического `flt` оставлена как в SQL; nonce защищает от коллизий нормализованных значений. Старые сообщения `PA_*` текущего отчёта не влияют на новый.

Это изоляция протокола между компонентами, **не дополнительная авторизация**: проверка доступа остаётся в SQL и Proteus. Корпоративная модель `postMessage` проверяется на отдельном борде владельцем.

Manifest и stamp проверяют версии полученных ответов, но не создают атомарный снимок нескольких физических таблиц при их замене. **Не открывай и не используй новый борд во время работы ноутбука.** Приёмка разрешена после его завершения, `ready` и проверок файла 11; затем принудительно обнови все чарты. Работа с бордом одновременно с публикацией в текущую поставку не входит.

При клике по подготовленному одиночному отчёту KPI, динамика и календарь появляются из уже принятого ответа каталога. Детали, которых в нём нет, показывают локальное ожидание на своей вкладке. Дополнительно проверяются текущий выбор, период, версия витрин и точное совпадение preview с принятой строкой `pv/pvh`; старый preview не используется после изменения фильтров. Предрасчёт есть для top500 отчётов и готовых периодов d/w/m/q, без людских фильтров и групп аудитории. Для собственного периода, коллекций, владельцев, множественного выбора и отчётов вне предрасчёта требуется полный ответ. В этом случае вкладки остаются доступны, устаревшие числа скрываются от дерева доступности и становятся `inert`; индикатор и скелетон показываются только в теле вкладки. Уникальные пользователи нескольких отчётов не складываются на клиенте. Пересоздание загрузчика не оставляет его навсегда «старым»: у каждого нового iframe свой instance ID. При пересоздании **главного iframe** с сохранёнными фильтрами старых загрузчиков интерфейс не угадывает выбор: показывает явное указание сбросить фильтры дашборда и обновить страницу целиком. Обычное повторное выполнение JS в том же iframe сохраняет состояние.

После завершения ноутбука принудительно обнови **весь** новый дашборд и сравни run_id с SQL Lab-проверками поставки. Совпадение трёх кэшированных ответов означает согласованность, но не доказывает, что они относятся к самому свежему запуску. Правила `cache_timeout=0/-1` в исторических документах противоречат друг другу; настройку нужно подтвердить на текущем форке, не переносить автоматически и не менять старый борд.

## UX и проверка

Внешний вид и расчётные функции прежних трёх виджетов сохранены. Изменения оболочки: единое окно, независимые ожидания блоков, понятные причины отказа, клавиатурный Enter/Space на строках с `role=button`, видимый фокус, reduced motion. «Как работать» запускает пошаговый гид с подсветкой настоящих элементов, кнопками вперёд/назад, Escape, возвратом фокуса и позиционированием по видимой части iframe. Каталог меняет ширину перетаскиванием разделителя или стрелками на клавиатуре. Каретка в его собственной шапке сворачивает каталог в узкую вертикальную полосу слева; клик по полосе возвращает каталог с прежним выбором и шириной. Отдельной панели управления и кнопок −/+ нет. В песочнице без localStorage раскладка сохраняется до пересоздания главного iframe. Между шапкой и панелями оставлен явный отступ; на узком экране элементы шапки переносятся без перекрытия кнопки гида. Основные вкладки, переключатели, поиск, сортировка и выбор остаются исходными.

Проверка в облаке: `python3 tools/parallel/test_ui.py` (Python Playwright + `/usr/bin/chromium`; установка зависимостей — в [TESTING.md](../tools/parallel/TESTING.md)). Это **тест транспорта на синтетических моках**, включая искусственное изменение echo; он не доказывает совпадение месячных/дневных чисел SQL. Скриншот `/tmp/pa-next-ui-default.png` снимается до искусственных изменений на исходном дневном моке. Числовая сходимость проверяется отдельным SQL-набором.

Дополнительные проверки: `python3 tools/parallel/test_board_css.py` — локальная модель документированной структуры holder/resizable, монтаж загрузчиков и режим редактирования (не проверка ленивого монтажа живого Proteus); `python3 tools/parallel/test_ui_controls.py` — календарь, семь условий ЦА, вкладки, таблица и тултипы у нижнего края видимой области.

Для проверки **на реальных ответах локального SQL** сначала сформируй синтетический мир по [TESTING.md](../tools/parallel/TESTING.md) и дождись завершения других процессов chdb. Экспорт: `PA_DB=<путь-к-миру> <python-с-chdb-2.1.1> tools/parallel/export_browser_fixtures.py --output /tmp/pa-next-periods`. Затем `python3 tools/parallel/test_ui_periods.py /tmp/pa-next-periods`. Экспорт содержит исходные ответы для 30 дней / 20 недель / 12 месяцев / 8 кварталов и SHA-256 SQL. Браузер меняет только транспортный nonce: бизнес-строки и эхо периода не переписываются. Проверяются KPI пользователей и MAU, все точки рядов, календарные подписи и равенство текстов KPI/каталога исходным рендерерам. Результат относится к синтетическому миру ClickHouse 24.8, не к данным прода.

Перед приёмкой на отдельном борде проверь: начальная загрузка трёх частей; 4 готовых и свой период; каталог→панель; люди→каталог; сброс; «Мои»; ЦА; пустой выбор; обновление ноутбука; ошибка одного загрузчика; быстрое несколько последовательных выборов; одинаковые числа с текущим отчётом на одинаковом срезе. Числа из разных событийных методологий сравнивать нельзя — вход должен быть одним и тем же.

Основной JS с встроенным логотипом после сжатия ≈408 КиБ; загрузчики ≈2 КиБ каждый. Тяжёлый интерфейс отправляется в запросе главного чарта, а интерактивные запросы данных используют маленький код загрузчиков. Это уменьшение размера JS в запросах взаимодействия; точное ускорение в секундах требует замера в Proteus.

Проверки нового взаимодействия: `test_ui_interactions.py` — полный гид, resize мышью/тачем/клавиатурой, скрытие/возврат каталога; `test_ui_preview.py` — немедленный preview и точное сравнение его рядов с отдельным SQL панели, смена фильтров и отклонение старых ответов. Команды и результаты дозагрузки — в `Проверки/UI — интерактивность и дозагрузка.md`; актуальная проверка каретки и боковой полосы — в `Проверки/UI — сворачивание каталога.md`.

## Согласованное оформление CROSS DATA

Справа в верхней строке находится акцентный знак с синей лентой, шириной 120 px и прозрачностью 0.60. В локальной загрузке основным остаётся сообщение; ниже — тонкая линия и подпись 110 px с прозрачностью 0.65. Линия анимирует только transform, а `prefers-reduced-motion` отключает её движение. При реальной ошибке анимация и бренд скрываются, причина и кнопка повтора остаются.

Изображение встроено один раз как data URI; внешняя сеть и дополнительные настройки Proteus не нужны. Исходник, подготовленный ресурс и воспроизводимая команда — в `src/assets/`. На ноутбуке шапка уплотнена как в согласованном макете, на узких контейнерах сохраняется перенос контролов. Перед получением деталей Who/Path/Coh показываются те же исходные KPI preview; формулы и набор предрасчитанных данных не менялись.
