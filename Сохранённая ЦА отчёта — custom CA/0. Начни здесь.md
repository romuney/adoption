# Сохранённая ЦА отчёта (custom CA) — начни здесь

Папка для доработки «ЦА отчёта»: владелец фиксирует целевую аудиторию своего
отчёта, она сохраняется через n8n в DLH (Trino), нода Helicopter
выгружает её в ClickHouse, отчёт PA NEXT подставляет её по умолчанию и
помечает такие отчёты в каталоге.

Весь проект лежит в этой же ветке (`custom-ca`). Актуальная поставка отчёта —
папка **«Параллельный отчёт — pa_next»** (начать с её «0. Начни здесь.md»,
данные — `DATA.md`). Навигация по репозиторию — `CLAUDE.md` в корне.

## Задание для модели, которая собирает флоу

Собери боевой n8n-флоу сохранения ЦА отчёта по файлу 2. Исходные данные:
макет (файл 3) и подпроцесс (файл 4).

1. Импортируй файлы 4 и 3 в n8n.
2. В файле 3 замени три ноды `Trino: владельцы`, `Trino: текущая версия`,
   `Trino: запись события` на **Execute Workflow → trino_query**. Имена нод
   сохрани.
3. В ноде «Конфиг и валидация» впиши реальные имена: журнал
   `pa_next_ta_event` (создаётся файлом 5) и таблицу метаданных дашбордов с
   владельцами. Владельцы должны совпадать с теми, что показывает отчёт:
   `owner_ad_login_list`, а если он пуст — `owner_login` (файл 2, §4). Если
   владельцы лежат в другом виде, перепиши только SQL в ноде `SQL:
   владельцы`, оставив колонку `login` на выходе.
4. Подключи `trino_query` к Trino: переменные окружения или способ, принятый
   в вашем n8n. Выход подпроцесса не меняй.
5. Не меняй валидацию, коды ответов, формат тела и порядок проверок — на них
   опирается отчёт. Если что-то пришлось изменить, запиши это в список
   отличий (ниже).
6. Проверь: `node "7. Проверки — симулятор флоу.js" "<твой флоу>.json"` —
   все кейсы `ok`, затем ручные кейсы из файла 2, §6, на тестовой копии журнала.

Ограничения: секреты (пароли Trino и подобное) — только в credentials или
переменных окружения n8n, не в JSON флоу. В DLH флоу только дописывает и
никогда не обновляет и не удаляет строки.

## Что вернуть (для встраивания в отчёт)

1. Полное имя журнала в Trino: `catalog.schema.pa_next_ta_event`.
2. Таблица владельцев: имя и поля, которые использованы.
3. URL webhook (боевой и тестовый, если есть разные).
4. Результат файла 8 — вывод консоли целиком.
5. Как нода `pa_next_ta` читает DLH: работает ли вариант из файла 6 (журнал
   виден из GP) или пришлось заменить параграф на python. Расписание ноды.
6. Список отличий от файла 2, если они есть.
7. Экспорт итогового флоу (JSON) — без credentials.

После этого со стороны отчёта: SQL каталога (секция `ta`, исключение
`pa_next_ta` из проверки версии), JS строки ЦА и каталога, регресс —
`1. План.md`, §3–§5.
