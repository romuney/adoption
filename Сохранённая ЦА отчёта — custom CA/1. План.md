# Сохранённая ЦА отчёта — план встраивания в PA NEXT

**Что хотим.** Владелец отчёта задаёт в строке «Целевая аудитория» условия
по атрибутам и структуре и фиксирует: «это ЦА моего отчёта». Дальше:

- когда смотрят этот отчёт, его ЦА **подставляется сама**, а не «по правам»;
- отчёты с утверждённой ЦА **помечены** в каталоге, по пометке можно фильтровать;
- сохранять и снимать ЦА могут **только владельцы отчёта**, это проверяет n8n.

```
строка «Целевая аудитория» ──fetch text/plain──▶ n8n pa_next_ta_save ──INSERT──▶ DLH (Trino) pa_next_ta_event
        ▲                                                                              │
        │                                          Helicopter-нода pa_next_ta, раз в 15–30 мин
        │                                          (DLH → GP pa_next_ta → gp_to_click)
        │                                                                              ▼
   JS 4 (src/*.js) ◀── SQL 5 каталог: секция ta ◀────────────────────── prod_proteus.pa_next_ta
```

## 1. Как это ложится на нынешний отчёт

В PA NEXT ЦА **одна на весь борд**: условия строки «Целевая аудитория»
уходят маской фильтров `ca_org_f`, `ca_spec_f`, `ca_stream_f`, `ca_hq_f`,
`ca_it_f`, `ca_head_f`, `ca_adg_f` (плюс поимённые `ca_login_f` и
`ca_master_f`). Без условий ЦА считается «по правам» каждого отчёта
(`pa_next_dash_ca`).

Сохранённая ЦА — это **те же значения тех же фильтров**, привязанные к
отчёту. Отсюда главное упрощение: чтобы показать отчёт по его ЦА, отчёт
просто применяет сохранённые значения той же маской, что и кнопка
«Применить». **SQL панели и шапки не меняется** — они получают обычный набор
`ca_*_f`.

Поимённые списки (`ca_login_f` / `ca_master_f`) не сохраняем. ЦА живёт по
атрибутам и каждый день пересчитывается по свежему штату: новый аналитик в
блоке сразу попадает в ЦА.

## 2. Данные

**DLH (Trino)** — журнал `pa_next_ta_event` (файл 5), пишет только n8n.
Каждая строка — версия ЦА одного отчёта.

**ClickHouse** — `prod_proteus.pa_next_ta`, одна строка на отчёт с
действующей ЦА. Выгружает нода `pa_next_ta` (файл 6) тем же `gp_to_click`,
что основная нода:

| Колонка | Тип | Смысл |
|---|---|---|
| `dashboard_id` | Int64 | отчёт |
| `version` | Int32 | версия |
| `f_org` … `f_adg` | Array(String) | значения `ca_*_f` (7 колонок) |
| `ca_size` | Int32 | размер ЦА при сохранении (справочно) |
| `comment` | String | «для кого отчёт» |
| `saved_by`, `saved_at` | String, DateTime | кто и когда |
| `loaded_at` | DateTime | когда нода выгрузила |

У этой таблицы **свой цикл обновления**: она не пишет в
`pa_next_manifest` и не несёт `_pa_next_run`. В SQL каталога её нужно
**исключить из проверки версии** (`pa_next_version`), иначе первая же
выгрузка ЦА отключит отчёт как «смешанные данные».

## 3. Датасеты

### SQL 5 — каталог: новая секция `ta`

По строке на отчёт из `pa_next_ta`, в том же 5-колоночном ответе:

| `section` | `g` | `k` | `parent` | `n` |
|---|---|---|---|---|
| `ta` | `active` \| `stale` | `dashboard_id` | компактный JSON: условия, `by`, `at`, `comment`, `size` (кириллица — через `cz`, как остальной ответ) | `version` |

`stale` — хотя бы одно значение больше не встречается в текущем штате
`pa_next_staffx`: путь `org` не совпадает и не является префиксом ни одного
`op`; `spec`/`stream` нет среди `sp`/`st`; кодов `hq`/`it` нет среди
`hqc`/`itc`; AD-группы нет в `pa_next_adg_size`. Проверка идёт по свежей
структуре на каждом запросе, нода её не делает.

Секция маленькая (сотни строк) и от фильтров не зависит, поэтому кэшу не
мешает.

### SQL 5 — вкладка «Аудитория», охват по отчётам (этап 2)

Сейчас без условий в шапке «Охват ЦА» каждого отчёта считается «по
правам». После внедрения логично считать по **его** сохранённой ЦА, если она
есть: зрители ∩ ЦА отчёта / размер ЦА отчёта. Тогда каталог по коллекции
сразу покажет охват каждого отчёта его же аудиторией. Это тяжелее (по
отчёту — свой набор условий над штатом), поэтому отдельный этап, с замером
скорости по «18. Как измерить скорость.md».

### SQL 7 — панель и SQL 3 — шапка

Не меняются.

## 4. Интерфейс (JS 4 из `src/*.js`, сборка `tools/parallel/build_ui.py`)

### Строка «Целевая аудитория»

| Состояние | Когда | Что видно | Действия |
|---|---|---|---|
| **ЦА отчёта** | область — ровно один отчёт, у него есть `ta`, человек не трогал условия | условия + бейдж «ЦА отчёта · v3 · a.petrova, 12.10» | все: изменить условия; «По правам» — временно снять |
| **Свои условия** | человек поменял условия | «Не совпадает с ЦА отчёта» | все: «Вернуть ЦА отчёта»; владелец: **«Сохранить как ЦА отчёта»** |
| **По правам** | у отчёта нет `ta` или её временно сняли | как сейчас | владелец: «Сохранить как ЦА отчёта», когда применены условия |

- **Подстановка.** При выборе одного отчёта с `ta` его условия ставятся в
  черновик и применяются тем же путём, что «Применить». Ручной выбор
  человека в этой сессии важнее: если он сам применил условия, отчёт их не
  перетирает, а только показывает «Не совпадает с ЦА отчёта».
- **Несколько отчётов в области.** Ничего не подставляется (ЦА у борда одна),
  подсказка: «У 3 из 5 отчётов есть своя ЦА — выбери один, чтобы смотреть по ней».
- **Кто владелец.** Логин — тот, что каталог уже получает
  (`current_username()`, ветка «Мои»). Владельцы — те же, что во вкладке
  «Владельцы» (`owns()`). Не владелец видит кнопку сохранения выключенной, в
  подсказке — кто владельцы. Решает всё равно n8n (403).
- **Сохранение** доступно, если применено хотя бы одно условие и нет
  поимённого списка. Если список есть: «Списки людей в ЦА отчёта не
  сохраняются — убери список или сохрани без него».
- **Окно сохранения:** условия, размер ЦА (текущее число с KPI), отличие от
  нынешней версии, поле «Для кого отчёт», «Сохранить». Запрос — `fetch` с
  `Content-Type: text/plain` (без preflight из песочницы), тело — по
  контракту из файла 2, §3. `request_id` — `crypto.randomUUID()` с запасным
  генератором.
- **Ответы:** 200 → бейдж сразу «ЦА отчёта · v4», пометка «у остальных
  появится в течение 30 минут»; 409 → «Пока ты редактировал, d.sokolov
  сохранил v4» и «Показать v4»; 403 → список владельцев; сеть недоступна →
  «Не удалось сохранить, попробуй ещё раз», условия не теряются.
- **Снять ЦА отчёта** — владельцу, с подтверждением.
- **Устаревшая ЦА (`stale`)**: подставляется, а владельцу показывается
  плашка «Значения больше не встречаются в структуре: … Пересохрани ЦА».

### Каталог

- У отчёта с `ta` — метка «ЦА», в подсказке кто и когда утвердил; у `stale`
  — та же метка с предупреждением.
- В переключателях каталога — «Только с ЦА отчёта». Фильтр клиентский, по
  секции `ta`, запроса не делает.
- Строки коллекций и владельцев — «ЦА: 7 из 12».

### Гид «Как работать»

Маршрут «Анализ ЦА» (`src/task-guide.js`) дополнить шагом «Зафиксируй ЦА
отчёта» для владельца.

Шаг 0 — первый, потому что от него зависит всё остальное. Отчёт живёт в
iframe-песочнице и сам в сеть не ходит. Если CSP Proteus или песочница не
пустят `fetch` к n8n, сохранять придётся иначе, например открывать в новой
вкладке форму n8n с подставленными условиями. Это другая схема доверия к
логину, её надо будет обсудить.

## 6. Решения, которые стоит подтвердить

1. **Подставлять ЦА отчёта автоматически** при выборе одного отчёта (как в
   плане) или только предлагать кнопкой «Смотреть по ЦА отчёта»?
   Автоматически — ближе к «по умолчанию показывать её», но меняет экран
   без клика.
2. **Охват в каталоге по ЦА каждого отчёта** (этап 2) — нужен ли сразу или
   после пилота.
