# Флоу n8n `pa_next_ta_save` — как собрать боевой

Макет `3. n8n — pa_next_ta_save (макет).json` можно импортировать и запустить
сразу: вызовы Trino в нём — заглушки с мок-ответами. Чтобы сделать флоу
боевым:

1. Создать журнал в DLH — файл 5.
2. Импортировать подпроцесс `4. n8n — trino_query (подпроцесс).json`. Он
   выполняет один SQL в Trino.
3. В макете заменить 3 ноды `Trino: …` на **Execute Workflow → trino_query**
   (§4).
4. Вписать имена таблиц в ноду **«Конфиг и валидация»**. Других мест с
   именами во флоу нет.
5. Прогнать кейсы: `node "7. Проверки — симулятор флоу.js" <ваш флоу>.json`,
   затем те же кейсы руками на тестовой таблице (§6).

Остальные ноды (валидация, проверки, сборка SQL, ответы) — готовая логика,
менять их не нужно.

---

## 1. На чём стоит

| Вопрос | Решение |
|---|---|
| Кто вызывает | `login` в теле — это `current_username()` Proteus. Каталог уже получает его в ответе датасета (`cache_key_wrapper(current_username())`, ветка «Мои»), отчёт кладёт его в запрос. Флоу ему доверяет. |
| Кто может сохранять | **все владельцы отчёта** и только они. Владельцы — по тому же правилу, что в отчёте (макрос `owns()`): непустые `owner_ad_login_list` в нижнем регистре, а если их нет — `owner_login`. |
| Что храним | значения фильтров строки «Целевая аудитория» **ровно в том виде**, в каком они уходят в `ca_<dim>_f` |
| Разрезы | `org`, `spec`, `stream`, `hq`, `it`, `head`, `adg` |
| Не храним | поимённые списки: `ca_login_f`, `ca_master_f` (их запрос получит 400) |
| Хранилище | DLH на Trino: журнал `pa_next_ta_event`, только дописываем |
| До отчёта | нода Helicopter `pa_next_ta` (файл 6) раз в 15–30 минут → `prod_proteus.pa_next_ta` |

Про доверие логину: кто знает адрес webhook, может отправить запрос с чужим
логином. Это осознанное допущение. Каждая запись подписана `saved_by`, так
что подмену видно в журнале. Если понадобится строже — включить в
Webhook-ноде `Header Auth` или пускать запросы только с хоста Proteus.

## 2. Значения разрезов

Флоу проверяет те же ограничения, что SQL датасетов (`7. SQL — панель.sql`,
блок «Применённая ЦА»). Иначе сохранится то, что отчёт потом молча отбросит.

| Разрез | Фильтр | Значение | Проверка во флоу |
|---|---|---|---|
| `org` | `ca_org_f` | путь `Блок › Департамент › …` (разделитель ` › `) — берёт и всех ниже | не больше 5 уровней, без пустых уровней |
| `spec` | `ca_spec_f` | специализация, название | непустая строка |
| `stream` | `ca_stream_f` | стрим, название | непустая строка |
| `hq` | `ca_hq_f` | код HQ | непустая строка |
| `it` | `ca_it_f` | код IT | непустая строка |
| `head` | `ca_head_f` | `'1'` — руководители, `'n'` — не руководители | не больше одного значения, только `1` или `n` |
| `adg` | `ca_adg_f` | AD-группа | непустая строка |

Внутри разреза условия складываются по ИЛИ, между разрезами по И (`condca()` в
SQL). Хотя бы одно условие обязательно. Существуют ли значения в структуре,
флоу не проверяет: выпадашки строки ЦА строятся из самих данных, а значение,
которое позже исчезло (подразделение переименовали), ловит SQL датасета по
свежему штату и помечает ЦА как устаревшую.

## 3. Контракт webhook

`POST /webhook/proteus/ta`, тело JSON:

```json
{
  "action": "save",
  "login": "a.petrova",
  "request_id": "6f1c2a9e-0d2b-4c1e-9a77-1f0c5c3e8b10",
  "dashboard_id": 14037,
  "expected_version": 2,
  "filters": { "org": ["Блок «Розница»"], "spec": ["Аналитик"], "head": ["n"] },
  "ca_size": 1240,
  "comment": "Отчёт для аналитиков розницы"
}
```

| Поле | Правило |
|---|---|
| `action` | `save` или `deactivate` (у `deactivate` нет `filters`) |
| `login` | `current_username()`; `[A-Za-z0-9._@-]`, сравнивается в нижнем регистре |
| `request_id` | uuid от отчёта, 8–64 символа `[A-Za-z0-9-]`; повтор не создаёт новую версию |
| `expected_version` | версия, которую человек видел на экране; `0`, если ЦА ещё не было |
| `filters` | только ключи из §2, ≤ 500 значений на разрез |
| `ca_size` | необязательно: размер ЦА, который показывал отчёт; хранится справочно |
| `comment` | необязательно, до 500 символов |

Ответы:

| Код | `error` | Когда |
|---|---|---|
| 200 | — | `{ok, action, dashboard_id, version, saved_by, saved_at, ca_size, sync: "scheduled"}` |
| 200 | — | повтор `request_id`: `{ok, replay: true, version, …}`, новой строки нет |
| 400 | `people_lists_not_allowed` | пришли `login` / `master` |
| 400 | `bad_action` · `bad_dashboard_id` · `bad_request_id` · `bad_expected_version` · `bad_ca_size` · `unknown_dims` · `bad_values` · `too_many_values` · `no_conditions` · `bad_comment` | запрос кривой; у `bad_values` в `detail` — разрез |
| 401 | `no_login` | логин не пришёл |
| 403 | `not_owner` | не владелец; в `detail.owners` — владельцы, отчёт покажет, к кому идти |
| 404 | `report_not_found` | у отчёта нет владельцев в источнике |
| 409 | `version_conflict` | пока человек редактировал, другой владелец сохранил; в `detail` — текущая версия и кто |
| 409 | `nothing_to_deactivate` | снимать нечего |

## 4. Ноды по порядку

Каждая нода передаёт дальше объект `{ok, cfg, DIMS, req, ctx}`. Нода `SQL: …`
добавляет к нему `sql`. Нода `Trino: …` возвращает только `{rows,
update_count}`: так ведёт себя Execute Workflow, поэтому следующая нода берёт
контекст через `$('SQL: …')`. Значит, замена заглушки на Execute Workflow
ничего не ломает ниже по цепочке.

| # | Нода | Что делает |
|---|---|---|
| 1 | **Webhook** | `POST proteus/ta`, ответ — из нод Respond |
| 2 | **Конфиг и валидация** | `cfg` с именами таблиц (**вписать здесь**); проверки §2–§3; условия без дублей, отсортированы |
| 3 | IF «Запрос корректен?» | нет → ошибка |
| 4 | **SQL: владельцы** | владельцы по правилу `owns()` из таблицы дашбордов |
| 5 | **Trino: владельцы** | → Execute Workflow |
| 6 | **Проверка: владелец?** | пусто → 404; логина нет среди владельцев → 403 |
| 7 | IF «Владелец?» | |
| 8 | **SQL: текущая версия** | последняя версия отчёта + поиск того же `request_id`, одним запросом |
| 9 | **Trino: текущая версия** | → Execute Workflow |
| 10 | **Сверка версии** | повтор `request_id` → 200 с прежним результатом; `expected_version` ≠ текущей → 409 |
| 11 | IF «Версия совпала?» | |
| 12 | **SQL: запись события** | **условный** `INSERT … SELECT … WHERE max(version) = expected AND request_id новый`; все строки экранированы |
| 13 | **Trino: запись события** | → Execute Workflow |
| 14 | **Проверка записи** | `update_count ≠ 1` → 409: кто-то успел записать между шагами 9 и 13 |
| 15 | IF «Записано?» → «Ответ: 200» | |
| — | «Тело ответа: ошибка» → «Ответ: ошибка» | сюда сходятся все ветки «нет»; наружу уходят только `error` и `detail`, без `sql` и `cfg` |

### Замена заглушки на Execute Workflow

Для каждой из 3 нод `Trino: …`:

- тип **Execute Workflow**, Source: Database, Workflow: `trino_query`;
- режим — по одному item, на вход идёт текущий item с полем `sql`;
- имя ноды оставить прежним: так понятнее, и симулятор (файл 7) подставит
  мок-ответы именно по этим именам.

Подпроцесс `trino_query` ходит в Trino REST (`/v1/statement`) и ждёт ответа.
Подключение берёт из переменных окружения n8n: `TRINO_URL`, `TRINO_USER`,
`TRINO_PASSWORD`, `TRINO_CATALOG`, `TRINO_SCHEMA`. Если у вас в n8n к Trino
уже ходят по-другому, используйте свой способ. Главное — сохранить выход:
`{ rows: [{колонка: значение}], update_count }`, где для INSERT `update_count`
— число вставленных строк.

### Что вписать в «Конфиг и валидация»

```js
T_EVENT:      '<catalog>.<schema>.pa_next_ta_event',   // из файла 5
T_OWNERS:     'Trino-таблица метаданных дашбордов',      // тот же источник, что owner_ad_login_list в ноде pa_next
OWNERS_ARRAY: 'owner_ad_login_list',                     // массив логинов владельцев
OWNER_ONE:    'owner_login',                             // запасной владелец
OWNERS_ID:    'dashboard_id',
```

Владельцы обязаны совпадать с теми, что видит отчёт (вкладка «Владельцы»,
«Мои»). В ноде pa_next они берутся из `owner_ad_login_list` источника
событий. Если в Trino есть таблица дашбордов с этим полем — берите её. Если
такого поля нет, а владельцы лежат строками (`dashboard_id`, `login`),
перепишите SQL в ноде `SQL: владельцы` на `SELECT DISTINCT lower(trim(login))
… WHERE dashboard_id = …`. Выход должен остаться прежним: колонка `login`.

## 5. Что делает отчёт после ответа

Это для встраивания, во флоу не нужно, но объясняет контракт:

- 200 → ЦА сразу показывается как утверждённая (из ответа), с пометкой «у
  остальных появится в течение 30 минут»;
- 409 `version_conflict` → «Пока ты редактировал, d.sokolov сохранил v4» и
  кнопка «Показать v4»;
- 403 → «Сохранить может владелец: …» со списком из `detail.owners`;
- 400 → текст ошибки; при нормальной работе отчёта такого быть не должно.

## 6. Проверка перед сдачей

Симулятор (файл 7) прогоняет все кейсы на мок-ответах, в том числе на уже
собранной боевой версии: ноды `Trino: …` он подменяет по имени.

```
node "7. Проверки — симулятор флоу.js" "<ваш флоу>.json"        # все 15 должны быть ok
node "7. Проверки — симулятор флоу.js" "<ваш флоу>.json" --sql  # плюс текст SQL каждого шага
```

Затем руками, на настоящем Trino и тестовой копии журнала:

| Кейс | Ожидание |
|---|---|
| владелец, первое сохранение, `expected_version: 0` | 200, `version: 1`, строка в журнале |
| тот же запрос ещё раз | 200, `replay: true`, новой строки нет |
| второй владелец поверх, `expected_version: 1` | 200, `version: 2` |
| не владелец | 403, в журнале ничего |
| устаревшая `expected_version` | 409 с текущей версией и `saved_by` |
| `filters.login` или `filters.master` | 400 `people_lists_not_allowed` |
| значение с апострофом (`O'Neil`) | сохраняется как есть |
| `deactivate` владельцем | 200; после запуска ноды `pa_next_ta` отчёта нет в `prod_proteus.pa_next_ta` |
| Trino недоступен | не 200 |
